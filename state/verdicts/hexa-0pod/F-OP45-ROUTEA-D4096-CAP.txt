STATIC FINDING 1 - THE MEASURED KERNEL IS CONFIG-IDENTICAL AT D=2048 AND D=4096 (rules out a/b/c)
================================================================================================
gemm_og17_b14 (MODE 8) is the kernel measured at BOTH D. Its tile / register / smem footprint is
a COMPILE-TIME CONSTANT, INDEPENDENT of the runtime matrix dimension D (M=N=K=D is a kernel
ARGUMENT, not a template parameter). Source evidence (wgmma_tf32_b14.cu:641, :653, :624-625):
  - TILE: `const int TM=128,TN=128` - fixed 128x128 output tile at every D.
  - ACCUMULATORS: `float d0[32],d1[32]` (line 653) = 2 fragments x 32 = 64 accumulator regs/thread.
    This is HALF the 128-reg footprint of the 4-accumulator (d0..d3) 128x256 tile.
  - SMEM: SWBUF = (TM+TN)*TKSW*4 = (128+128)*32*4 = 32768 B/stage; at NST=3 = 98304 B ~= 96 KB/CTA
    + the NST mbarriers. Verdict header confirms: "2 CTA/SM, 96.0 KB/CTA dynsmem" - SAME line for
    D=2048 AND D=4096 (the D=4096 sweep lines 82-85 use MODE8 NST=3, identical 96 KB/CTA).
  - OCCUPANCY: 96 KB/CTA -> 2 CTA/SM on H100 (228 KB/SM ceiling; 2*96=192<228). HELD at both D.
  - PDEP only deepens the wgmma SCOREBOARD depth (wgmma.wait_group PDEP), NOT the smem ring
    (source comment :623-624: "NO smem growth beyond NST ... occupancy unchanged at the same NST").
=> The register count, the smem footprint, AND the occupancy (2 CTA/SM) are BYTE-FOR-BYTE THE SAME
   binary/config at D=2048 and D=4096. The kernel does not recompile or re-tile per D. Therefore:
   (a) register-SPILL - EXCLUDED. Spill is a property of the compiled binary; the binary is
       identical at both D. If it didn't spill @2048 (it didn't - 315 TFLOP/s @ 2 CTA/SM), it
       cannot spill @4096. The "256-elt register-realloc" in the verdict footnote refers to MODE 5
       (gemm_og17_t256, d0..d3 = 128 regs, line 760), a DIFFERENT kernel that was NOT the D=4096
       MODE 8 datapoint. Misattribution: the footnote borrowed the W12/MODE5 closed-neg cause.
   (b) occupancy-DROP at larger D - EXCLUDED. 2 CTA/SM at both D (same 96 KB/CTA). Occupancy is
       not a function of D for a fixed-tile kernel. (Occupancy DOES halve at NST>=4 -> 1 CTA/SM,
       verdict line 79, but that is the NST lever, swept and rejected at BOTH D, not a D-effect.)

STATIC FINDING 2 - THE GAP IS DRIVEN BY cuBLAS GAINING +24.6% AND own LOSING -9.9% AT LARGER D
================================================================================================
Decompose the ratio change 1.08x -> 1.50x into the two operands (verdict verbatim numbers):
  cuBLAS-TF32:  342.5 -> 426.8 TFLOP/s   = 1.246x   (+24.6%)   <-- cuBLAS SCALES UP with D
  own (MODE 8): 315.0 -> 283.9 TFLOP/s   = 0.901x   (-9.9%)    <-- own SCALES DOWN with D
  ratio:        1.08x  -> 1.50x          (1.50/1.08 = 1.39 = 1.246/0.901, exact decomposition)
=> ~63% of the gap-widening is cuBLAS getting FASTER at D=4096; ~37% is own getting SLOWER.
   Neither operand is "flat with a ptxas ceiling" - both MOVE, in OPPOSITE directions.

WHY cuBLAS GAINS at D=4096 (static reasoning, the dominant term):
  - At D=4096 the GEMM has 8x the FLOPs (4096^3/2048^3 = 8x) but 4x the output tiles (1024 vs 256)
    and 2x the K-slabs (nks=K/32: 128 vs 64). cuBLAS picks a DIFFERENT, larger, deeper-pipelined
    kernel/heuristic per shape (split-K, bigger tiles, persistent CTAs, wave quantization tuned to
    132 SMs). Its arithmetic intensity rises and its fixed per-launch / tail-wave overheads
    amortize over 8x the work -> it climbs toward its own roofline.
  - The hexa MODE 8 kernel uses a SINGLE fixed 128x128 plain-launch schedule (gridDim =
    (D/128)x(D/128) = 32x32 = 1024 CTAs at D=4096), one CTA per output tile, no split-K (forbidden
    by g5 - split-K forfeits the bit-exact accumulation order), no persistent rasterization in
    MODE 8 (the persistent + swizzle lever is MODE 7, not MODE 8). It cannot adapt its tile to the
    larger problem, so it does not capture the large-D scheduling gains cuBLAS does.

WHY own LOSES -9.9% at D=4096 (static reasoning, the secondary term):
  - 2x the K-slabs (nks 64->128) means 2x the K-loop iterations per tile, each ending in
    `wgmma.commit_group` + `wait_group PDEP` + `__syncthreads()` (line 692-694). The per-slab
    pipeline-drain + sync overhead is paid 2x as often relative to a fixed prologue; the deeper-D
    K-loop has more serialization points. (PDEP=1 was the D=4096 best, not PDEP=2 - the deeper
    dual-issue that helped @2048 did NOT help @4096, consistent with the K-loop being more
    drain-bound at larger nks.)
  - WAVE QUANTIZATION is NOT the cause (computed statically): 132 SMs x 2 CTA/SM = 264 resident
    CTAs. D=2048: 256 tiles / 264 = 0.97 wave-efficiency. D=4096: 1024 tiles / 264 = 3.879 ->
    ceil 4 waves -> 1024/(4*264) = 0.970 wave-efficiency. IDENTICAL 0.970 at both D - the tail
    wave is NOT what differs. (This rules out the naive "D=4096 has a worse partial last wave"
    story; the plain launch is coincidentally equally well-quantized at both sizes.)
