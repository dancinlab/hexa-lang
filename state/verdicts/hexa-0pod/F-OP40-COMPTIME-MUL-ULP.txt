ROOT-CAUSE CLASSIFICATION (g0 — which side diverges + WHY, with evidence)
────────────────────────────────────────────────────────────────────────────
The OP-37b assumption (host comptime `*` rounds differently from clang) is
FALSIFIED. Decisive evidence chain, all self-measured:

1. THE MULTIPLY IS IEEE-CORRECT.  In the SAME runtime, parse_float("0.254829592")
   * parse_float("0.284496736") then f64_to_bytes_le(product) gives bits
   4589888465602041182 = python EXACTLY. rt_mul / hexa_mul is `float_of(a) *
   float_of(b)` (self/rt/core.hexa:225 / runtime_core.c:8169) — a SINGLE isolated
   fp64 multiply, round-to-nearest, NO FMA (no `+` to contract with). clang's own
   compile-time fold of the same `let m3 = (0.254829592)*(0.284496736)` (the
   STRUCTURAL-3 Phase-A path emits the un-evaluated C expr at codegen.hexa:5423,
   clang folds it) ALSO gives bits-182. -O0==-O2 identical across all 125 cases →
   no FMA contraction, no x87 excess precision. BOTH sides round IEEE-identically.

2. THE PARSE IS BYTE-EXACT.  Confirmed by OP-37b and re-confirmed: parse_float
   → strtod gives exact operand bits. A 125-case strtod-replica (a*b in plain C,
   correctly-rounded operands) = python with MAX 0 ULP everywhere.

3. THE SERIALIZE IS THE BUG.  The fold computes the CORRECT product (bits-182),
   then `_cf_float_node(f)` → `format_float_sci(f, 17)` ("%.17e") to bake the C
   literal. In the SELF-HOST build the runtime's snprintf is `#define`d to the
   hand-rolled `hxlcl_snprintf`/`hxlcl_vsnprintf` (self/runtime.c:2095, a
   freestanding no-libc printf whose own comment says "Not bit-exact with libc's"
   — naive digit extraction + round-half-up at peek-next-digit), AND
   HEXA_HAS_HEXA_RT_STDLIB routes `format_float_sci` to the hexa-source
   `rt_format_float_sci` (stdlib/runtime/numeric.hexa:213), a hand-rolled
   mantissa-via-`x/p10` + `x*mult+0.5`-truncate decimal formatter. Neither is
   correctly-rounded. PROVEN: feeding the EXACT correct product (bits-182) into
   format_float_sci(·,17) returns "7.24981871602117067e-02", which re-parses to
   bits-183 — a 1-ULP-high round-trip. (Plain libc snprintf("%.17e", bits-182)
   gives the correct "…116967"; the divergence appears ONLY through the runtime's
   overridden snprintf / hexa-source formatter.)

DIVERGING SIDE  = the COMPTIME FOLD's float→decimal SERIALIZATION (host hand-
                  rolled %.17e). IEEE-CORRECT SIDE = clang / runtime (the
                  `let`-decl emitted as `hexa_float((L)*(R))` is computed by clang
                  and is bit-exact). This is the SAME class CLAUDE.md's
                  `stdlib_trig_libm` directive warns about: hand-rolled arithmetic
                  is fragile (here, not round-trip-exact).

WHY OP-37b under-counted it as "rare": OP-37b measured a 6-case file and saw the
residual on 1 product; the 125-case sweep shows it bites ~13% of computed folds
(any product whose mantissa the hand-rolled formatter mis-rounds) — REAL, not
rare. The negation/additive-identity idioms OP-37 made byte-exact (preserved
source text, never re-serialized) were correctly 0 ULP and still are.

THE FIX (self/codegen.hexa — additive, +86/−9, no deletions)
────────────────────────────────────────────────────────────────────────────
`_cf_float_node(f)` now serializes the folded double as a bit-EXACT C99 hex-float
literal (`0x1.<mant>p<exp>`) via the new `_cf_float_hexlit(f)`, built from the raw
IEEE-754 bits with INTEGER ops ONLY (float_to_bits → sign/exp/mantissa via
`>>`/`&`, 13 mantissa nibbles formatted by `_cf_nib_hex`, trailing-zero strip).

lead-`0` exp `-1022`. clang parses a C hex-float to the EXACT double it names —
no decimal rounding step at all, so the lossy hand-rolled formatter is bypassed
entirely. No runtime edit, no new algorithm, no .tape. The hex-float string emits
verbatim into the existing `hexa_float(<value>)` wrapper (FloatLit emit path
unchanged, codegen.hexa:5187).

Validation of the integer-only formatter: a python mirror of the exact algorithm
round-trips 2013 random doubles (subnormal..1e308, ±0) with 0 mismatches, and

implementation reproduces these byte-for-byte and clang re-parses them to the
