GOAL
  OP-19 (#3002) + OP-19b (#3008) + OP-19c (#3016) proved flame's deterministic
  dt_exp/dt_erf folds byte-IDENTICAL on 3 platforms — arm64-macos (Darwin libm),
  x86-linux (aiden, glibc), arm64-linux (pi5, glibc). OP-19c's KEY finding: the libm
  exp/erf divergence is an OS/libc effect (glibc vs Darwin), NOT an ISA effect (pi5
  arm64-linux tracked aiden x86-linux on the libm path, not the arm64-macos machine
  it shares an arch with). The {x86,arm64}×{linux,macos} matrix's 4th cell (x86-macos)
  has NO pool host (retired Intel Macs). This OP tests the result HARDER with a 4th
  DISTINCT ENVIRONMENT that supplies a DIFFERENT libc entirely — musl (Alpine) — the
  strongest test of "no libm dependence left": if dt_* match on musl too while libm
  folds DIVERGE across glibc/musl/Darwin, that is definitive.

 2. CAN HEXA RUN ON MUSL 0-POD? — YES, but only with a TEST-ONLY runtime shim
    (a REAL hexa-runtime↔musl portability bug found + characterized + worked around)
────────────────────────────────────────────────────────────────────────────────
  hexa's compiler binary (hexa.real) is a glibc-dynamically-linked PIE → cannot run
  under musl. But `hexa run` = transpile .hexa → C, then `clang … self/runtime.c -lm`
  → native binary. So the GENERATED C of each oracle was transpiled on aiden (working
  glibc hexa, `self/native/hexa_v2 oracle.hexa out.c`), then COMPILED + RUN inside the
  Alpine/musl container. The produced binary links MUSL libc/libm:
      ldd /tmp/exp_musl →  libc.musl-x86_64.so.1 => /lib/ld-musl-x86_64.so.1   (PROOF)
  This is a legitimate musl test of the generated code: dt_exp/dt_erf are pure FP
  (libc-independent); libm `exp`/`erf` resolve to MUSL's libm.

  THREE musl-specific BUILD blockers surfaced + fixed (build-only, NOT numeric):
   (a) self/native/net.c includes <sys/un.h>; runtime.c's `#define strlen hxlcl_strlen`
       (line 1488) mangles musl's `size_t strlen(const char*)` proto (glibc's <sys/un.h>
       doesn't redeclare strlen). Fix: clang `-include sys/socket.h -include sys/un.h …`
       so the headers parse BEFORE the macro. (header-ordering only)
   (b) Alpine base clang ships no linker → `-fuse-ld=lld` (+ apk lld).
   (c) lld couldn't find crtbeginS.o/-lgcc → apk gcc + libgcc (CRT + libgcc).

  THEN a REAL RUNTIME BUG (not build — genuine musl incompatibility), hit at process
  init BEFORE any oracle code, gdb backtrace:
      SIGSEGV in hxlcl_getenv (runtime.c:913)  ← _hexa_init_mem_cap (constructor)
                                                ← musl do_init_fini / __libc_start_init
    ROOT CAUSE: runtime.c:34 priority-101 ctor `hxlcl_capture_environ(int,char**,char**
    envp){ hxlcl_environ = envp; }` + `#define environ hxlcl_environ`. The runtime's own
    comment states it relies on "Darwin/dyld passes (argc,argv,envp,apple) to init
    routines" — and glibc has the same .init_array constructor-args extension. **musl
    does NOT pass argc/argv/envp to constructors** (they are called with NO args), so
    `envp` is garbage → hxlcl_environ = garbage → _hexa_init_mem_cap's getenv("HEXA_MEM_
    LIMIT") walks garbage → segfault, before main(). A genuine hexa-runtime↔musl libc-
    ABI incompatibility (constructor calling convention), latent on glibc/Darwin.
    WORKAROUND (TEST-ONLY, disclosed; NOT committed, NOT in any shipped path): patched a
    THROWAWAY copy self/runtime_muslpatch.c so the ctor reads musl's real `extern char
    **__environ` instead of the un-passed envp. This touches ONLY env capture — every
    math / dt_* / libm path is byte-IDENTICAL to the unpatched runtime. With the shim,
    both oracles run cleanly on musl (EXP-RC=0, ERF-RC=0).
  HONEST: the env-capture ctor ABI bug is a real follow-up for the runtime (out of
  OP-19d's measurement scope — fixing it is a guarded runtime source change + its own
  verify/PR). It is at process init and is INDEPENDENT of the fold math.
