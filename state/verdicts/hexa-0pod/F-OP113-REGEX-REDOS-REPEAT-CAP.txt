F-OP113-REGEX-REDOS-REPEAT-CAP — cap the native regex `{n,m}` counted-repeat to close a ReDoS / resource-exhaustion vector
========================================================================================================================

GOAL (g5): SELF-SELECT a genuinely FRESH (non-crypto, not-yet-audited) high-value
security surface and find the RESOURCE-EXHAUSTION / DoS side OP-105 did not touch —
a parser/matcher that ALLOCATES or LOOPS proportional to an untrusted declared
count WITHOUT a sanity cap (the unbounded-WORK side, distinct from OP-105's
read-OOB which we bounded to the buffer). Surveyed axes below.

RESULT: 🔴 → FIXED. stdlib/regex/native.hexa (the pure-hexa, zero-libc backtracking
regex engine — the matcher behind compiler/lint/config pattern matching) parses the
`{n,m}` counted-repeat with NO upper bound on the count. A counted repeat expands in
`_re_run_repeat` to `n` MANDATORY matcher iterations, each calling `_re_repeat_marker`
which does `nodes.push([12,...])` — so the parsed count `n` is BOTH the loop bound AND
the allocation count. A malicious 11-byte pattern `a{999999999}` therefore forces
~1e9 iterations + ~1e9 array growths (multi-GB allocation + near-infinite loop) =
CWE-1333 (ReDoS) / CWE-400 (uncontrolled resource consumption). FIXED by capping the
parsed bound at `_RE_MAX_REPEAT()` = 100000 (far above any realistic stdlib/config use;
RE2 caps at 1000, Java/.NET/Python at small bounds) and FAILING the parse on overflow
(`p.ok = false` → all three entry points return false via their `!p.ok` guard) rather
than silently truncating to a wrong count. Pure-additive (+20 / −1 lines); no valid
match semantics change (every previously-accepted realistic pattern still parses;
only DoS-scale counts are rejected).

NOTE (OP-87/88/107 lesson): the installed ~/.hx/bin/hexa resolves `use` to a STALE
Jun-1 bundle that lacks this edit, so the verification surface is a VERBATIM-INLINED
hermetic leaf oracle (`hexa run`, no `use`) of the patched parse logic — trust the
port-of-source over the stale binary.

VERBATIM REPRO (pre-fix) — hermetic leaf oracle inlining _re_parse_repeat + _re_run_repeat
──────────────────────────────────────────────────────────────────────────────────────
  parsed count from a{999999999} = 999999999
  a{1000000} -> matcher iterations = 1000000
  a{999999999} -> matcher iterations EXCEED oracle sentinel (>= 5,000,000); real code
                  would run 999999999 iterations + push that many marker nodes (multi-GB).

  → A 9-byte digit run parses to count 999,999,999 with NO cap (`lo = lo*10 + digit`,
    unbounded), and `_re_run_repeat`'s `lo>0` branch recurses that many times, each pushing
    a `[12,...]` marker node onto `nodes`. Tiny pattern → near-infinite loop + OOM.

──────────────────────────────────────────────────────────────────────────────────────
FIX (stdlib/regex/native.hexa) — surgical cap, fail-closed
──────────────────────────────────────────────────────────────────────────────────────
  + @pure fn _RE_MAX_REPEAT() -> int { return 100000 }
  in the {n,m} lo-accumulate loop:   if lo > _RE_MAX_REPEAT() { p.ok = false; return -1 }
  in the {n,m} hi-accumulate loop:   if hi > _RE_MAX_REPEAT() { p.ok = false; return -1 }
  `{n,}` unbounded (hi = -1) is still allowed — its mandatory part `lo` is capped above,
  and the open-ended tail is bounded by input length in _re_run_repeat (progress guard).
