================================================================================
MOTIVE — the unchecked-error-sentinel bug class
================================================================================
Many stdlib functions signal failure by RETURNING A SENTINEL rather than
raising: `index_of` / `find` / `find_index` return `-1` on a miss, a lookup
returns an empty/default struct, a search returns `len(x)` (one-past-end) on
not-found. The BUG is a CALLER that USES that sentinel WITHOUT checking it —
`arr[index_of(x)]` when index_of can return -1 (→ reads `arr[-1]`), a slice
`xs.substring(find(a), …)` / window `xs[find(a) .. find(b)]` where a -1 / len
sentinel makes a wrong or inverted window. This is the silent-wrong-data
class: no crash, no exception — just a quietly incorrect result (and
sometimes a negative-index OOB).

================================================================================
NEGATIVE-INDEX SEMANTICS (probed — decides silent-wrong-value vs OOB)
================================================================================
`hexa run` 0.1.0-dispatch probes:

  arr = [10, 20, 30]; arr[-1]            -> index -1 out of bounds (len 3)
  arr[idx_of("ABC","X")]  (miss -> -1)   -> index -1 out of bounds (len 3)
  "hello".find("z") / .index_of("z")     -> -1   (miss sentinel confirmed)
  to_int("abc") / parse_int("zz")        -> error: to_int: not an integer

FINDINGS:
- `arr[-1]` is a HARD FAULT (bounds-checked) — NOT a Python-style wrap to the
  last element. So an unchecked `-1` finder-sentinel used as an INDEX is a
  crash / DoS; used in a SLICE or arithmetic it is silent-wrong-data. Either
  way the guard is mandatory.
- `.find` / `.index_of` builtins return `-1` on a miss (the class
  precondition).
- `to_int` / `parse_int` ERROR on malformed input — they do NOT silently
  return 0. So the "parse silently yields 0 on bad input → wrong sum" sub-
  class is vacuously closed for the builtin numeric conversions.
