GOAL: OP-4 (F-OP4-5070-COVERAGE) mapped the flame FUSED training step (cuBLAS lane: fused
valley LN+gelu+copy + single-launch AdamW + transpose-elim) vs torch on the 5070 and found

per-launch + separate-cuBLAS-handle overhead floor (the GEMM is tiny at B=1, so ~4-11 kernel
launches dominate; torch's inductor fuses into ~2 kernels AND graph-captures via cudagraph
trees). OP-4b TESTS that attribution: wrap the SAME fused per-step DAG in a CUDA graph
(cudaStreamBeginCapture/EndCapture -> cudaGraphInstantiate -> cudaGraphLaunch) so the whole
step replays as ONE launch, and re-measure graph vs eager (un-captured OP-4 baseline).

  IF graph << eager -> the floor was per-launch overhead; ratio narrows toward torch.compile.
  IF graph == eager -> the launch floor was NOT the binding cost; the small-B loss is cuBLAS
       GEMM-rate-bound, NOT launch (the honest closed-neg, matching H100 BENCH-6).

============================ WHERE THE SMALL-B LOSS LIVES =================================
NOT launch. GEMM-RATE. Graph capture collapses ALL per-op launch/sync overhead into one
replay; if the small-B floor were launch-bound, the ratio would have dropped. It moved
<2%. Therefore on the RTX 5070 the small-B step wall is dominated by the cuBLAS GEMM
execution itself (plus, for BF16, the f32->bf16 cast kernels' memory traffic), not by the
cost of issuing the launches. The 5070's per-launch overhead is already small relative to
even a tiny-M cuBLAS GEMM at these D — there is no launch floor left for a graph to remove.
torch.compile wins the small-B cells because its inductor path runs a FASTER/fused GEMM-glue
schedule (fewer, fatter kernels + cuBLASLt heuristics tuned for small-M), not because it
saves launches that flame is paying. This is the SAME structural result as H100 BENCH-6:
graph-capture ~1.0x => residual pinned to GEMM-throughput, not launch.

This corroborates and SHARPENS the broader campaign finding (MEMORY: ~3x cap is structural
op-DAG, interpreter-elimination FALSIFIED, megastep INFERENCE-only): the flame step's gap to
torch is a GEMM-schedule/fusion-quality gap, not a launch-elimination opportunity. The
launch-elimination lever (graph capture) is now CLOSED-NEGATIVE on the consumer 5070 too.

================================ HONEST SCOPE (g5) ========================================
- Graph capture is BIT-EXACT (gate max|dW'|=0 every cell) + deterministic — it changes
  nothing mathematically, exactly as designed. So it is a SAFE optimization to ship; it just
  doesn't HELP on this workload/card.
- This was scoped (OP-4b note) as a SMALL-B-only probe. It did not move FP64 (already
  compute-bound, ~1.2x, confirmed unmoved) and was never expected to touch large-B
  (cuBLAS-GEMM-rate-bound). The probe's job was to test the small-B launch-floor hypothesis;
  the hypothesis is REFUTED for the 5070.
- flame's consumer-card value remains its IDENTITY (byte-exact / device-resident /
  deterministic / no-LLVM / torch-free), NOT raw step-rate. torch.compile is faster on every
  small-B cell, and graph capture does not change that.

CONCLUSION: OP-4b CLOSED-NEGATIVE (honest). CUDA-graph capture of the fused step is bit-exact
+ deterministic but gives ~1.0x (1.00-1.02x) on the RTX 5070 — the small-B loss to
torch.compile is GEMM-rate-bound, not launch-overhead-bound. The worst cell (BF16/D=2048/B=1)
stays 14.64x vs 14.66x. Launch-elimination is exhausted as a lever on the consumer card.
