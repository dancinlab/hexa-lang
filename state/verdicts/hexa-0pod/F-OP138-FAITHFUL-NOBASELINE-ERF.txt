 3. ROOT CAUSE — compiler-correctness fix invalidated a stale golden (case (b))
────────────────────────────────────────────────────────────────────────────────
  Neither the oracle nor the golden source changed:
    · stdlib/flame/op19b_crossplatform_erf.hexa — git diff vs its creation
      commit e9bbcefeb (#3008) is EMPTY (byte-identical).
    · tool/fold_ci_gate.sh golden — unchanged since abe447aa8 (#3060, OP-34).
  So the SOURCE is fixed; the drift is purely from the COMPILER that builds
  ./hexa in CI.

  Mechanism: the golden was recorded (OP-19B #3008 → OP-34 #3060, 2026-06-12)
  under the PRE-float-fix compiler whose compile-time float const-fold serialized
  via a LOSSY `%g` (6 sig-digit) / `%.17e` path. dt_erf's rational constants are
  9–10 significant digits:
    0.3275911 · 0.254829592 · 0.284496736 · 1.421413741 · 1.453152027 · 1.061405429
  Under the OLD serialize these were silently TRUNCATED/ROUNDED before folding,
  so the dt_erf result carried lossy constant bits. OP-37/OP-37b/OP-40/OP-132
  (#3069/#3073/#3084/#3300, all AFTER the golden was pinned) replaced that with a
  SHORTEST-round-trip serialize (strtod-exact, IEEE-correct inverse). Those
  constants now fold to their CORRECT bits → a DIFFERENT, MORE-correct dt_erf
  value: 1088281529475491513 / 2045849491002578884.

  Why dt_exp (CEBWD) still matches its golden: its constants are 0.25 / 1.0 /
  2.0 / 12 — all serialize bit-identically under either path → no shift. Only the
  high-precision dt_erf constants moved. This is exactly the discriminating
  signature of "lossy-serialize-fixed", not "codegen broke FP semantics".

  → CLASSIFICATION: (b) STALE / MIS-CAPTURED GOLDEN. The OLD golden was the
  artifact of a now-fixed compiler bug. NOT (a) a machine-independence
  regression (cross-platform byte-eq holds 3/3). NOT (c) a flake (the new value
  is stable across runs and platforms).
