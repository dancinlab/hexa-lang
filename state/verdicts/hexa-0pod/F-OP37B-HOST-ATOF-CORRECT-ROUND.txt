THE RESIDUAL (decisive — flagged by OP-37 / PR #3069 HONEST RESIDUALS §1)
────────────────────────────────────────────────────────────────────────────
OP-37 fixed the `0.0 - <float literal>` NEGATION idiom byte-exact by preserving
the operand's exact source TEXT (additive-identity special-cases). It left a
documented residual: folds that actually COMPUTE a new value from RE-PARSED
operands (e.g. `let a = 1.5 * 0.1`) re-parse via `to_float` → `__hx_to_double`
→ `hxlcl_atof`, a naive digit-accumulator (n=n*10+d; frac*=0.1), NOT a
correctly-rounded strtod. OP-37 narrowed the SERIALIZE side to %.17e but left
the PARSE side at ≤1 ULP per operand. OP-37b asks: is it real on current source,
how large exactly, and is a correctly-rounded host parse tractable without
breaking the self-host byte-eq fixpoint?

────────────────────────────────────────────────────────────────────────────
ROOT CAUSE (the two parse paths in the runtime — the smoking gun)
────────────────────────────────────────────────────────────────────────────
The compiler's const-folder ran in the hexat host binary. The host runtime has
TWO string→double paths:
  · `to_float(x)` → `__hx_to_double(STR)` → `hxlcl_atof(HX_STR(v))`
       hxlcl_atof = NAIVE accumulator (runtime.c:270, n=n*10.0+d; frac*=0.1;
       exp via repeated *10.0) — NOT correctly-rounded, up to 1 ULP off.
  · `str.parse_float()` → `hexa_str_parse_float(STR)` → `strtod(HX_STR(s),NULL)`
       (runtime.c:3034) — C-standard CORRECTLY-ROUNDED.
`_cf_as_float` (self/codegen.hexa:9874) used `to_float(lit.value)` — the lossy
path. Routing the FloatLit text through `parse_float()` selects the correctly-
rounded strtod path that already exists in the SAME runtime.

WHY this is the g0/g4 winner (Occam): hxlcl_atof's C body lives only in the
untracked, build-time-assembled `self/runtime.c` (gitignored; `self/runtime.hexa`
is the marker SSOT, and the hxlcl_atof body is part of the irreducible C
bootstrap substrate — NOT editable from tracked repo source). So fixing
hxlcl_atof itself, or porting Eisel-Lemire, would touch a non-tracked foundation
file and is unnecessary: the correctly-rounded strtod path is ALREADY present
and is selected purely by which tracked-source codegen builtin the folder calls.
The fix is one expression in self/codegen.hexa — no runtime edit, no new algo.

THE FIX (self/codegen.hexa — additive, minimal, no deletions)
────────────────────────────────────────────────────────────────────────────
1. `_cf_as_float(lit)` — for a FloatLit, parse via `lit.value.parse_float()`
   (→ hexa_str_parse_float → strtod, correctly-rounded) instead of
   `to_float(lit.value)` (→ hxlcl_atof). The IntLit branch is unchanged
   (to_float and parse_float agree on integers — no fraction to mis-round).
   Cures the computed-fold operand parse for * / + - and sqrt/min/max
   (all reach operands through _cf_as_float).
2. `abs` float fold (comptime_eval Call path) — preserve the operand's EXACT
   source text (abs of a literal is the same magnitude, sign stripped) instead
   of `to_float`-parse + `_cf_float_node`-reserialize. Byte-exact, matching
   the OP-37 additive-identity discipline. (Was the one remaining direct
   `to_float(a.value)` site in the computed-fold family.)
