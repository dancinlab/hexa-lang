SCALE DEFECT FOUND? — ONE STAGING TRAP found + documented (NOT a production
load-path code defect):
  STALE-INSTALL MODULE-RESOLUTION TRAP. With a stale installed hexa (the local
  Jun-1 ~/.hx build), `use "self/ml/tokenizer_bpe"` inside a stdlib/flame-
  RESIDENT file resolves source-dir-relative (stdlib/flame/self/... absent)
  and then falls back to the INSTALL's own self/ tree — which still carries
  the PRE-OP-28b byte->unicode map (256+byte formula). The first staging run
  silently picked that stale copy and reproduced the EXACT pre-fix failure
  (byte-127 glyph U+017F instead of U+0121; spot ids 221/254/255 -> UNK 0;
  multilingual round-trip 2/6) even though the repo source is fixed.
  Diagnosis chain: vocab.json keys verified RAW UTF-8 on disk; hexa
  json_parse handles multi-byte keys at full 151643-key scale (probe: all
  contains-key true); production tok internals correct — divergence isolated
  to build_byte_to_char() returning the OLD table => import resolution, not
  parse. CURE (documented in the oracle header): run from a REPO-ROOT COPY
  (source-dir-relative resolution then picks the repo's own fixed modules).
  A relative `use "../../self/..."` is NOT a fix — the lib's inner
  `use "self/..."` then splices the stale copy as a duplicate (compile error).
  The production load path itself (json_parse at 2.7MB / 151643 keys, glyph
  bijection, merge ranks, id maps) showed NO defect at real scale.
