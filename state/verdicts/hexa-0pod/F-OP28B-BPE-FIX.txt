CONTEXT — OP-28's residual.
  OP-28 (#3041) proved the BYTE-LEVEL corpus token pipeline (tokenize->pack->
  batch, V=256) is deterministic + machine-independent (pure integer, byte-eq
  run-to-run + cross-platform). It flagged a RESIDUAL: the BPE path
  (stdlib/flame/flame_bpe_corpus_lib.hexa, V=151936 — the real Qwen vocab) was
  NOT cleanly 0-pod-runnable because its byte<->unicode map collided / broke the
  real-Qwen round-trip. OP-28b fixes that map so the BPE path is also
  determinism-provable.

THE BUG (root cause — verified empirically on the local hexa runtime)
  self/ml/tokenizer_bpe.hexa::build_byte_to_char did NOT build the canonical
  GPT-2/Qwen bytes_to_unicode(). It had TWO distinct defects:

  (1) CHR-TRUNCATION / WRONG-GLYPH on the printable range. It used `chr(i)` for
      printable bytes. `chr(n)` in hexa (runtime.c hexa_chr_byte) masks to a
      single byte (n & 0xFF) and returns a 1-byte string:
        probe: chr(288) -> bytes [32]   == chr(32) == space  (COLLISION hazard)
               chr(161) -> bytes [161]  (RAW byte 0xA1)
      But the canonical map (and Qwen's vocab.json) stores the Latin-1 printable
      range (bytes 161..172, 174..255) as the UNICODE CODEPOINT U+00A1..U+00FF,
      i.e. UTF-8 0xC2 0xA1.. :
        probe: from_char_code(161) -> bytes [194,161]  (UTF-8 U+00A1, canonical)
      So token strings for those bytes never matched the real vocab. (And had
      build_byte_to_char ever used chr on the 256+ range, chr(256+i) would have
      collapsed to chr(i), the exact space-collision the old header warned of.)

  (2) WRONG CODEPOINT FORMULA on the non-printable range. It used
      `from_char_code(256 + i)` (codepoint = 256 + byte_value). The canonical
      map assigns the non-printable bytes codepoint 256 + n where n is a RUNNING
      COUNTER incremented once per non-printable byte (ascending byte order).
      The two agree only for bytes 0..32 and DIVERGE for every byte >= 127 —
      exactly 35 bytes (127..160 and 173):
        byte 127: canonical U+0121, old code U+017F   (WRONG)
        byte 160: canonical U+0142, old code U+01A0   (WRONG)
      ... so those 35 glyphs never matched the real vocab either.

  NOTE on OP-28's framing: OP-28 attributed the residual to "hexa chr()
  truncates to a byte". That IS one of the two defects (defect 1) — but the
  deeper, dominant defect was (2), the non-canonical codepoint formula. Both
  are fixed. from_char_code (the UTF-8 codepoint encoder) was already correct
  and is the right primitive; the fix is to use it for the WHOLE table with the
  canonical running-counter formula, and to never use byte-truncating chr in
  the byte->unicode map.

THE FIX (surgical — self/ml/tokenizer_bpe.hexa::build_byte_to_char)
  build_byte_to_char now emits the canonical GPT-2/Qwen 256-entry bijection:
    printable byte b (b in 33..126 | 161..172 | 174..255) -> from_char_code(b)
                                                             (codepoint == b)
    every OTHER byte (ascending order)                     -> from_char_code(256 + n)
                                                             (running counter n)
  - from_char_code is the UTF-8 encoder (1-byte for ASCII, 2-byte for
    U+00A1..U+00FF and U+0100..U+0143) — NOT byte-truncating chr.
  - Pure integer / table build: the codepoint sequence is fixed + ascending,
    so the table is byte-identical run-to-run and across machines. No libm, no
    float, no hash-ordered dict (OP-28 determinism discipline).
  - The decode side (bpe_decode + build_char_to_byte) was already UTF-8-
    codepoint-aware (lead-byte-sized slicing) and consumes the SAME table, so
    the inverse is consistent — no decode change needed.
  - flame_bpe_corpus_lib.hexa header updated: limitation RESOLVED.
