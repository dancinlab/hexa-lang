 F-OP34-FOLD-CI-GATE — machine-independence FOLD checks wired into CI as a
 regression gate: dt_exp/dt_erf golden folds asserted per-platform
 HEXA-0POD OP-34 (deep-dive round-9 branch ④) · 0-GPU · 0-pod · ZERO vast · $0
════════════════════════════════════════════════════════════════════════════════

GOAL
  The cross-platform determinism oracles (OP-19 dt_exp + OP-19b dt_erf folds)
  exist on main but NOTHING ran them in CI — a regression (someone reintroduces
  libm on a deterministic site, breaks a canonical fold order, or a codegen
  change alters FP semantics) would land SILENTLY. OP-34 adds a low-blast-radius
  CI gate that runs the deterministic-fold oracles on the 3 CI platforms and
  FAILS if any fold drifts from the recorded golden values.

────────────────────────────────────────────────────────────────────────────────
 1. FEASIBILITY CHECK → WIRING CHOICE (the cheapest honest wiring)
────────────────────────────────────────────────────────────────────────────────
  INSPECTED .github/workflows/nobaseline-gate.yml (faithful-nobaseline): each of
  the 3 platform jobs (darwin-arm64 macos-latest · linux-x86_64 ubuntu-latest ·
  linux-arm64 ubuntu-24.04-arm) builds a WORKING ./hexa from the shared release
  path (tool/release_build: Stage 0b edge-pulls build/runtime.a → Stage 0a-pre
  build/hexat → Stage 0/1/2 → ./hexa) and already asserts `./hexa --version`.
  → A built hexa binary IS available in those jobs ⇒ per the feasibility ladder,
  the fold checks are APPENDED THERE (cheapest: zero extra builds, zero new
  jobs, the exact same 3-platform matrix the machine-independence result needs).

  THE .c=0 SEAM (why `hexa run` works there with the seeds removed): `hexa run`
  = `hexa build` + exec; the final link honors HEXA_PREBUILT_RUNTIME
  (self/main.hexa resolve_prebuilt_runtime — ".c-graduation Phase-3" seam) and
  links the prebuilt archive instead of compiling the absent self/runtime.c.
  The faithful jobs leave Stage 0b's archive at build/runtime.a; the gate
  script auto-exports HEXA_PREBUILT_RUNTIME=$PWD/build/runtime.a when present.

  SHAPE (the OP-5b forge-runtime-warn-gate / OP-19f musl-ctor-abi-gate
  discipline): the logic lives in ONE SSOT script — tool/fold_ci_gate.sh —
  runnable locally (`sh tool/fold_ci_gate.sh [hexa-bin]`); the CI step is a
  thin wrapper. One step per platform job, right after the './hexa runs'
  assert, before release_package. Runtime cost <5 s/platform (each oracle runs
  in <0.1 s; the only cost is two tiny `hexa build` compiles).

  PATH-SCOPING NOTE: nobaseline-gate triggers on push/PR to main with NO paths
  filter (it is the release-safety gate). The fold step rides that trigger —
  which is CORRECT coverage here: a fold regression can come from compiler/
  codegen changes ANYWHERE, not just from edits to the flame stdlib or the
  oracle files, so a paths-filtered trigger would under-cover. The added cost
  is <5 s on a job that already runs.

────────────────────────────────────────────────────────────────────────────────
 5. LOW BLAST RADIUS (the OP-5b/OP-19f discipline) — CONFIRMED
────────────────────────────────────────────────────────────────────────────────
  · The gate runs ONLY the two SELF-CONTAINED oracles (no `use`, no flame
    stdlib import, no repo-wide compile/scan) — grandfathered or unrelated code
    can never fail it.
  · It asserts ONLY the 3 deterministic fold lines; the platform-dependent
    LIBM lines are not compared.
  · Failure modes: (a) a fold drifts from its golden = the REAL regression the
    gate exists for; (b) the oracle fails to build/run on the CI platform = a
    real breakage of `hexa run` on a release platform (also worth failing on,
    and the faithful job's own asserts would usually catch it first).
  · The script is the SSOT; the 3 YAML steps are thin wrappers. No new
    workflow, no new trigger surface, no required-check changes.
