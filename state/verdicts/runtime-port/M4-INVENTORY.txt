KEY STRUCTURAL FINDING — the rt_* delegation is ALREADY DEEP in core too.
runtime_core.c carries 88 HEXA_HAS_HEXA_RT_STDLIB guards delegating to 83
distinct rt_* hexa-native fns. 57 hexa_* core fns are therefore B-PORTED
(hexa impl already lives in self/rt|runtime + stdlib/runtime *.hexa; the C body
is a standalone-link FALLBACK only). The "portable surface" of runtime_core.c is
NOT virgin — most of it was already drained by the rt_* stdlib campaign.

KEY FEASIBILITY FINDING — the remaining B-OPEN set is a dict_keys-class wiring
gap, NOT a porting frontier. Of the 9 B-OPEN leaves, THREE
(hexa_str_char_code_at · hexa_str_concat · hexa_str_substring) ALREADY HAVE a
matching hexa impl in the rt-stdlib (rt_str_char_code_at / rt_str_concat /
rt_str_substring all exist in self/rt|runtime|stdlib *.hexa) — they simply lack
the HEXA_HAS_HEXA_RT_STDLIB delegation guard in runtime_core.c. This is exactly
the dict_keys pattern (the leaf looked un-ported but the hexa walk already
existed). The required builder builtins also already landed: B1 str_from_bytes_n
+ hexa_strbuf_alloc length-carrying builder (STRBUILDER-FEAS, #2632) covers the
concat/substring assembly. So the genuine NEW porting yield here is tiny.
