CORRECTION of the prior M2-hexa_dict_keys.txt BLOCKED verdict
------------------------------------------------------------------------
The prior verdict claimed: "rt_map_keys (map_keys_pure) operates on a SEPARATE
pure-hexa functional map representation built via rt_map_new/rt_map_set — a
different data structure with its own ordering ... no apples-to-apples RUNEQ."
This is FALSE for the actual code path. map_keys_pure(m) is literally
`return keys(m)` (self/runtime/map_pure.hexa L42) — it consumes the SAME
HexaVal map object and the SAME native HexaMapTable as the C SSOT. There is no
second map type on this path. The rt_map_new/rt_map_set functional builders
exist but are NOT what rt_map_keys reads. The leaf was mis-classified.

THE NATIVE MAP REP (read from self/runtime_core.c — READ-ONLY, gitignored)
------------------------------------------------------------------------
HexaMapTable (runtime_core.c L1048-1065) — open-addressing hash + parallel
insertion-order arrays:
    typedef struct {
        HexaMapSlot* slots;     // power-of-2 hash table (FNV-1a, hmap_find)
        HexaVal*     vals;      // parallel values (slot-indexed)
        int          ht_cap;
        char**       order_keys;// INSERTION-ORDER key ptrs (-> slots[].key, strdup'd)
        HexaVal*     order_vals;// insertion-order values

  HexaMapSlot (L1042): { char* key (strdup'd, NULL=empty); uint32_t hash; int order_idx; }
  HexaMap     (L1088): { HexaMapTable* tbl; int len; }
  HexaVal.map_ptr (L1116) -> HexaMap*;  HX_MAP_TBL(v) (L1147) = (v).map_ptr->tbl.

C SSOT key walk (hexa_map_keys, runtime_core.c L3025-3034, #else branch — the
canonical body):
    arr = hexa_array_reserve(arr, t->len);
    for (i = 0; i < t->len; i++) arr = hexa_array_push(arr, hexa_str(t->order_keys[i]));
ORDER GUARANTEE: strict insertion order; overwrite of an existing key updates
order_vals[order_idx] in place and does NOT append (no duplicate key). Keys are
strdup'd char* in slots[].key; order_keys[i] aliases that pointer; hexa_str()
re-wraps to a TAG_STR HexaVal. NUL-bearing keys: keys are NUL-terminated char*
internally so an embedded 0x00 truncates at the slot level (a pre-existing C-rep
property, NOT introduced by any port — the ported body inherits it identically).

THE PORT (ready to apply — hexa-source only)
------------------------------------------------------------------------
Transliteration of the C SSOT loop using the existing primitives. Add to
self/rt/map_ops.hexa (and point rt_map_keys at it / or fix map_keys_pure):

    @pure pub fn rt_dict_keys(m) {
        let n = __map_raw_len(m)
        let mut out = []
        let mut i = 0
        while i < n {
            out.push(__map_order_key_at(m, i))
            i = i + 1
        }
        return out
    }

To close the leaf at the canonical surface, make the keys() port non-recursive
by replacing self/runtime/map_pure.hexa L42 body `return keys(m)` with the same
order-walk (map_values_pure/map_entries_pure should likewise use
__map_order_val_at instead of re-deriving via keys(m)+m[k], removing their
hidden re-entry too). Then rt_map_keys → map_keys_pure walks order_keys directly
= byte/order-identical to hexa_map_keys' C #else body.

RUNEQ EVIDENCE (LOCAL on mini — no ghost/pool)
------------------------------------------------------------------------
1. Equivalence-by-construction: __map_order_key_at(m,i) reads t->order_keys[i]
   via hexa_str(); __map_raw_len(m) reads t->len. These are the IDENTICAL fields
   the C SSOT hexa_map_keys #else loop reads. The ported body is a structural
   1:1 transliteration of that loop. They cannot diverge in length, order, or
   key value (same pointers re-wrapped by the same hexa_str()).
2. C SSOT ground truth captured via surface keys() (== hexa_map_keys path) on
   /tmp/runeq_keys_ground.hexa, installed toolchain:
     many        keys() -> [k1] [k2] [k3] [zzz] [a]          (strict insert order)
     overwrite   keys() -> [x] [y]                            (no dup on rewrite)
     forty (0..39) keys() -> [0]..[39]                        (collision-stress, ordered)
     empty       len(keys()) == 0
3. Codegen-lowering proof: compiling the rt_dict_keys body emitted, byte-for-
   byte, direct calls — `HX_MAP_LEN(m)` for __map_raw_len and
   `__map_order_key_at(m, i)` for the accessor (verified in the emitted .c) —
   confirming the INSTALLED hexat already recognizes + lowers all three builtins
   to the SSOT-field accessors. (The local link failed only because the pinned
   install's runtime.o/runtime.h predate the de-staticized __map_order_* / the
   HX_MAP_LEN fn-form decl — a STALE-INSTALL artifact, resolved by the standard
   runtime regen the implementation PR runs, not a representation gap.)
A full end-to-end numeric RUNEQ (same map → C path vs ported path, both at
runtime) requires that runtime regen, which is exactly the codegen byte-eq
gated step (below) and out of scope for a feasibility-only round. The three
lines of evidence above are conclusive for the feasibility verdict.
