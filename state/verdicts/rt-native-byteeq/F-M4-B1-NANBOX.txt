────────────────────────────────────────────────────────────────────────────────────────
1. THREE EXISTING NATIVE EXPRESSIONS OF THE B1 CTORS (all landed, pre-this-batch)
────────────────────────────────────────────────────────────────────────────────────────
(a) codegen-inlined `_hv_load`/`_hv_store` (compiler/codegen/arm64_darwin.hexa ~1090):
    every int/float/bool/void literal lowers DIRECTLY to `movz tag` + `movz/ldr payload`
    register writes — no runtime call. This IS hexa_int/bool/void/float inlined at the
    call site. x86_64 carries the full {tag,payload} pair model (#3462) + M1 landed the
    25 `__hx_*` leaf intrinsics (grep -c __hx_ x86_64_linux.hexa = 73).
(b) HEXA_RT_SELFEMIT byte-emitter (self/codegen/runtime_arm64.hexa rt_hexa_void/int/bool/
    float/enum_str/enum_str_v, bundled by test/native_build/emit_hexa_val_ctors_o.hexa):
    each ctor = 12 bytes = 3 hand-encoded aarch64 instructions exporting the strong
    `_hexa_*` symbol. Under -DHEXA_RT_SELFEMIT runtime_core.c emits them as `extern` and
    ld64 binds every callsite to the self-emit .o. Self-documented byte-confirmed vs
    `as -arch arm64` (otool) + JIT-exec-correct. ACTIVATED only by the opt-in
    HEXA_RT_SELFEMIT=1 env (arm64 Mach-O only) in tool/build_hexa_cli.hexa — NOT by the
    authoritative byteeq gate.
(c) `__hx_*` bind-whitelist intrinsics (compiler/check/bind.hexa ~1221) for the read side
    (__hx_tag/__hx_payload_*) — the value-destructure counterpart of the ctors.

The C `#else` bodies (self/runtime_core_emit.hexa ~1505) are the 1-line aggregate literals:
  hexa_int(n){return (HexaVal){.tag=TAG_INT,.i=n};} … 3-way #ifdef:
  #ifdef HEXA_RT_SELFEMIT extern  /  #else  C body  /  #endif   (per ctor).

────────────────────────────────────────────────────────────────────────────────────────
4. WHY NO `stdlib/runtime/nanbox.hexa` WAS AUTHORED (c9 + c16, empirical)
────────────────────────────────────────────────────────────────────────────────────────
Probe (RAN, ./build/hexat on aiden):
    pub fn hexa_int_probe(n: int) -> HexaVal { return HexaVal { tag: 0, payload: n } }
  transpiled to:
    HexaVal hexa_int_probe(HexaVal n) { … return … HexaVal(hexa_int(0), n); }
  i.e. a HexaVal struct-literal in hexa source emits a CALL to `hexa_int` — the very ctor.
  numeric.hexa's own comment says it plainly: "hexa typing doesn't model the HexaVal union
  directly" (that's why hexa_abs is split into rt_abs_int/rt_abs_float — you cannot
  construct/destructure the union in hexa source). A hexa-source nanbox.hexa would be
  SELF-RECURSIVE / impossible; the byte-emitter rt_hexa_* (mechanism (b)) is the correct
  and complete native form. Authoring a redundant/circular file would violate c9/c10.
CLASSIFICATION (c16): this is NOT a fixpoint break and NOT a lowering bug — it is a
  "already-native via the only viable mechanism" finding (twin of F-LEGB-RTSTR). The
  task's nanbox.hexa premise rested on a HexaVal-source-constructibility that does not hold.
