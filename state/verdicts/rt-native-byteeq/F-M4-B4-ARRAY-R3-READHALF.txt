3. WHY IT CANNOT SHIP-INTEGRATE THIS ROUND (🧱 WALL-3 — bootstrap-transpile gap, c16 ≥2 lenses)
────────────────────────────────────────────────────────────────────────────────────────
First attempt imported array_core.hexa into compiler/main.hexa. The aprime/release build
flattens main.hexa → hexat (C-transpile bootstrap) → gcc. hexat does NOT lower the raw-mem
intrinsics (only self/codegen.hexa gen2 does):
   RAN: build broke — ap_post.c: '__hx_payload_add'/'__hx_ptr_load64'/'__hx_make_val'/'__hx_tag'
        undeclared (the intrinsics emit as undefined C calls under hexat).
Lens-1 (transpile): hexat ≠ gen2 — only gen2 inlines these leaves. Confirmed: grep shows the
  raw-mem intrinsics are used ONLY in standalone scratch .hexa gates (native-compiled directly),
  NEVER in any compiler-imported module; array_core was the first such import = the break.
Lens-2 (runtime path): the rt-stdlib runtime bodies enter via hexat too (extract_runtime_hi.sh
  runs hexat); runtime_hi.hexa (the rt_str native-seed SSOT) uses ZERO __hx_ intrinsics by
  design — it is dual-path (hexat C + frozen .s). A raw-mem-intrinsic body has NO hexat-
  transpilable form, so it can enter ONLY via the native-emitted frozen .s seed
  (self/native/runtime_hi_x86_64.s precedent), ar'd into runtime.a (build_aprime.sh:241-263).
Lens-3 (build precedent): build_native_linux_* EXPLICITLY excludes the array stdlib from the
  compiler flatten closure + C-link-fills rt_array_pop/shift (lines 117-140) — the architecture
  deliberately keeps array primitives out of the hexa closure.
DECISIVE REGRESSION (why gating was mandatory): build_aprime/release DEFINE
  HEXA_HAS_HEXA_RT_STDLIB. With the delegation under that macro, hexa_array_get/set took the
  native arm → link FAILED (`undefined reference to rt_array_get_native`, RAN). So the
  delegation MUST be gated behind a dedicated DEFAULT-OFF macro until the seed lands.
