RUNG 2 BOUNDARY (the precise remaining gap — runtime string-print)
==========================================================================
A program calling a RUNTIME builtin with a primitive arg fails:
  $ cat hi.hexa
    fn main() { print("hi") ; exit(7) }
  emit OK (valid ELF x86-64 .o), link OK, RUN -> stdout=[<value>] rc=208
  (expected stdout=hi rc=7).

ROOT CAUSE — incomplete HexaVal arg ABI in the x86_64 STMT_CALL path:
  HexaVal is a 16-byte struct `{ HexaTag tag; union { i64 i; char* s; … } }`
  (self/runtime_core.c:1007). Under the SysV AMD64 ABI a 16-byte struct
  passes in a register PAIR: arg0 -> rdi(tag):rsi(payload),
  arg1 -> rdx:rcx, arg2 -> r8:r9; INTEGER/POINTER returns are rax:rdx.
  The x86_64 backend (compiler/codegen/x86_64_linux.hexa STMT_CALL loop,
  ~L951-964) currently materialises only ONE register per arg (the payload),
  omitting the tag eightbyte, and does NOT box int/bool runtime returns.
  Emitted asm for print("hi"):  `mov rdi, .LCstr0 ; call hexa_print_val`
  — passes the raw cstr pointer where hexa_print_val expects a {tag,payload}
  HexaVal -> prints `<value>`. exit(7): `mov rdi, 7 ; call hexa_exit`
  -> 7 read as a malformed HexaVal -> rc 208.

  The arm64 backend does this correctly via `_hv_load(buf, arg, lo, hi)`
  (arm64_darwin.hexa L1961-1996): tag in the lo reg, payload in the hi reg,
  per arg pair, plus _builtin_ret_box for int/bool returns. The same
  16-byte two-eightbyte ABI must be implemented for x86_64 (a `_hv_load`-
  equivalent emitting `mov tag_reg, TAG ; mov payload_reg, value` into the
  rdi:rsi / rdx:rcx / r8:r9 pairs, + rax:rdx return boxing). This also
  affects the pre-existing x86_64 array/map runtime-call emits
  (hexa_array_push etc., L724-862) which likewise pass HexaVal in one reg.

  This is a self-contained NEXT codegen milestone ("x86_64 HexaVal 16-byte
  SysV struct-by-value arg/return ABI"), NOT a correctness defect in the
  ret/arithmetic/branch codegen proven above.
