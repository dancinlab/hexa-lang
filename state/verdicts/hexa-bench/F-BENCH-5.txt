==================== (1) ISA PROBE — which TF32 tensor-core MMA does sm_120 accept? =====
Probe self/native/mma_sm120/probe_mma_sm120.cu, one ptxas pass per family for -arch=sm_120
on aiden's CUDA 13.0.88 (the cheap ISA check, done FIRST). VERBATIM:

  === BENCH-5 ISA PROBE  arch=sm_120  release 13.0, V13.0.88 ===
  [TRY_MMA_SYNC] ACCEPTED  (ptxas emitted SASS for sm_120)
  [TRY_TCGEN05]  REJECTED
      ptxas ... error : Arguments mismatch for instruction 'tcgen05.mma'
      ptxas fatal   : Ptx assembly aborted due to errors
  [TRY_WGMMA]    REJECTED
      ptxas ... error : Instruction 'wgmma.fence' not supported on .target 'sm_120'
      ptxas ... error : Instruction 'wgmma.mma_async with floating point types' not
                        supported on .target 'sm_120'

  FINDINGS (the load-bearing answer):
   • mma.sync.aligned.m16n8k8.row.col.f32.tf32.tf32.f32 — YES. The Ampere+ warp-level
     synchronous tensor-core TF32 MMA ASSEMBLES on sm_120/CUDA13. This is the portable
     path; it is what BENCH-5's own-GEMM uses.
   • tcgen05.* (Blackwell 5th-gen) — NO (as written). The mnemonic 'tcgen05.mma' is KNOWN
     to ptxas 13.0.88 (the error is "Arguments mismatch", NOT "not supported"/"unrecognized")
     — i.e. the family EXISTS in the sm_120 assembler but needs the full Blackwell operand
     protocol (tensor-memory tcgen05.alloc + tmem address + a 64-bit instruction descriptor
     + tcgen05.ld/st to drain tmem accumulators). It is NOT a drop-in like mma.sync and was
     out of scope for a one-session port; the portable mma.sync path covers the goal (own-
     GEMM RUNS on the consumer card). HONEST: tcgen05 is reachable on CUDA13 but bleeding-
     edge / multi-instruction-protocol, deferred.
   • wgmma.* (Hopper sm_90a warpgroup-async) — NO. Re-confirms BENCH-3: the Hopper MMA
     family is genuinely absent from the sm_120 ISA ("not supported on .target sm_120").

==================== (2) sm_120 TF32 own-GEMM — build + GATE + perf =====================
self/native/mma_sm120/owngemm_sm120.cu. PORTS OG10's tiling SPIRIT (block tile 64x64 +
BK=16 smem stage + register-resident FP32 accumulators + RN-to-TF32 operand rounding) onto
the mma.sync.m16n8k8 warp-MMA primitive (NOT the wgmma warpgroup-async primitive OG10 uses,
which sm_120 rejects). 4 warps/block (2x2), each warp owns a 32x32 output = a 2x4 grid of
m16n8 fragments. C[M,N]=A[M,K]@B[K,N] row-major, TF32 matmul / FP32 accum.

GATE (g5): rel-RMS / max|delta| of the own-GEMM vs a cuBLAS-TF32 (COMPUTE_32F_FAST_TF32)
reference, square shapes. ALL PASS (<<1e-2):
  S=768   rel-RMS 1.332e-05  max|delta| 1.151e-05  PASS
  S=1024  rel-RMS 3.019e-05  max|delta| 1.406e-05  PASS
  S=2048  rel-RMS 1.743e-05  max|delta| 1.936e-05  PASS
  S=4096  rel-RMS 6.952e-05  max|delta| 2.199e-05  PASS
→ the sm_120 own-GEMM is CORRECT (TF32-tolerant) at every shape. It RUNS — the BENCH-3
  "OG10 can't compile for sm_120" weakness is REMOVED: flame now has an own-GEMM that
  executes on the consumer card.

PERF (standalone square GEMM, own-GEMM vs cuBLAS-TF32 on aiden, verbatim):

HONEST: a naive (no cp.async double-buffer, no register-blocking beyond the warp tile, no

analogous to OG10 being 6.09x off cuBLAS on Hopper. The WIN is that it RUNS + is correct
on the consumer card, NOT that it beats cuBLAS.

==================== DOES own-GEMM-on-consumer-card NARROW THE TF32 GAP? =================
YES — partially. The OWN120 own-GEMM shrinks the BENCH-1 naive gap and, crucially, KILLS
the naive kernel's batch-scaling blowup (where naive went 3.06x->9.67x as B grew, because
the naive tiled kernel does not scale with the larger GEMM M):

   B | NAIVE (this run) | OWN120 | cuBLAS-proxy (ceiling) | OWN120 shrink-vs-naive
   --+------------------+--------+------------------------+-----------------------
   1 |      3.06x       | 2.81x  |        2.15x           |   1.09x
   2 |      4.05x       | 3.01x  |        2.24x           |   1.35x
   4 |      5.53x       | 3.16x  |        2.26x           |   1.75x
   8 |      9.67x       | 4.73x  |        2.79x           |   2.04x

 • OWN120 lands BETWEEN naive and the cuBLAS proxy at every batch — exactly as predicted
   for a real (non-cuBLAS) own-GEMM. The biggest win is at B=8: 9.67x -> 4.73x (a 2.04x
   shrink), the regime where the naive kernel was worst.
 • OWN120 does NOT reach the cuBLAS-proxy ratio (2.79x vs 4.73x @B8). That residual is the
   own-GEMM's ~3.2x-off-cuBLAS standalone perf — i.e. a hand-written warp-MMA GEMM doesn't
   match cuBLAS, mirroring OG10's 6.09x-off-cuBLAS on Hopper. The cuBLAS proxy was
   explicitly the OPTIMISTIC ceiling; OWN120 closes LESS, as BENCH-3 forecast.
 • NO torch-parity regime in TF32 (torch still 2.8-4.7x ahead with the own-GEMM; ~2x of
   the cuBLAS-proxy residual is launch/glue/occupancy, not GEMM). FP64 B>=4 remains flame's
   only ahead regime (BENCH-2, unchanged — torch has no FP64 tensor-core path).
