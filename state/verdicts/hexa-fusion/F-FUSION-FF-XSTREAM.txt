VERDICT: 🔴 CLOSED-NEGATIVE — the between-GEMM valley is NOT reclaimable by
cross-stream concurrency on this kernel at these (real MoE) shapes.
================================================================================
byte-eq:  PASS — max|Δ| = 0.000e+00 at EVERY shape. Concurrency changes nothing
          about the math (same kernel, same inputs, only overlap). The probe is
          SOUND: any wall/util delta is pure scheduling, not a correctness artifact.

valley reclaimed: ~0 (and NEGATIVE at scale). The premise — that the per-expert
          conv UNDER-FILLS the H100, leaving a reclaimable valley — is FALSIFIED
          for this kernel: the naive O(d²·T) MAC k_conv_single is COMPUTE-BOUND
          and SATURATES the H100 (util MEAN=MEDIAN=100%) even SERIALLY, at the
          SMALLEST swept width (d=512, only 4×32=128 CTAs/launch but each CTA does
          a d-deep MAC inner loop → SMs never idle). There is no idle valley
          between the E serial launches to overlap.

          Consequence: adding streams cannot raise an already-100% util, and it
          ACTIVELY HURTS wall once the device is saturated — concurrent streams
          contend for the same SMs / L2 / HBM and serialize with scheduling
          overhead: speedup 1.31x (d=512) → 0.59x (d=1024) → 0.47x (d=2048),
          monotonically worse as the per-launch work grows. The single 1.31x at
          d=512 is tail-overlap of the LAST few launches (launch+drain latency
          amortization), NOT util reclaim (util was already 100%) — and it does
          not survive to any real MoE width.

HONEST (g5): this is the predicted modest/negative outcome. The FF-XSTREAM premise
          assumed the valley kernels under-fill; on the H100 the per-expert conv
          is compute-bound and already fills the device, so cross-stream
          concurrency has nothing to reclaim and a saturated device punishes it.
          The "valley" the megakernel/fusion lines target is the INTERPRETED
          host-glue between ops (per-window token loop + eager AdamW + inter-op
          glue — see CUDA-graph + async + whole-step closed-neg), NOT GPU-side
          kernel under-fill that streams could overlap. FF-XSTREAM bounds the
          stream-concurrency lever at ≤0 for the real-shape MoE conv: the valley
          is NOT reclaimable by concurrency. Consistent with the ASYNC axis
          (F-FUSION-ASYNC-UTIL-AB) which already found single-process multi-stream
          async does not lift util.
