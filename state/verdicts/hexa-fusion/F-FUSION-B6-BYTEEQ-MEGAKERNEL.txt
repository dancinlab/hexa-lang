SMEM BUDGET MATH (the task's risk #1 — RESOLVED, no overflow):
  P1's _hx_dev_conv_tf32 uses ZERO __shared__ — it accumulates each output cell in a
  per-thread REGISTER (`float acc`) reading A and B directly from global memory; there is
  no smem tiling. So the 49152B "FP64 tiles are 2× TF32 → overflow" concern does NOT apply:
  the FP64 swap turns the 4-byte register `float acc` into an 8-byte register `double acc`
  (register file, NOT shared memory). __shared__ bytes in the megafwd region: 0 (TF32) → 0
  (FP64). No smem overflow, no tile shrink, no extra grid.syncs. The register-resident
  naive-conv scheme is exactly WHY byte-eq breaks (sequential k-order ≠ cublasDgemm tiled
  k-order) — the smem-free design that dodges risk #1 is the same design that triggers
  risk #2.

FINDING
════════════════════════════════════════════════════════════════════════════════
BYTE-EQ leg — FALSIFIED (🔴 CLOSED-NEGATIVE). max|Δ| ≠ 0 at EVERY config:
  D512 first_ce Δ = 9.0e-16, D1536 first_ce Δ = 1.8e-15 — and CRUCIALLY this delta is
  already present at EPOCH-1 first_ce, i.e. after ONE forward pass, before any training
  compounding. That isolates the cause unambiguously to the GEMM REDUCTION ORDER: the FP64
  own-GEMM accumulates k sequentially (one thread per output), cublasDgemm accumulates k in
  tiled/blocked order; the two produce different IEEE-754 last-bit roundings. This is NOT a
  bug to fix at the wiring level — it is structural: the eager path IS cublasDgemm, and any
  GEMM that fits inside a persistent cooperative kernel (a kernel cannot call cuBLAS) uses a
  DIFFERENT summation order, so max|Δ|=0 vs cublasDgemm is unreachable for the own-GEMM
  family. (Corroborates F-FUSION-P1B-TILED-GEMM, which measured own-vs-cuBLAS GEMM-element
  max|Δ| of 1e-6…1e-3 directly — cuBLAS is a correctness ORACLE within fp tol, never the
  byte-eq roofline.) The B6 premise — that the #2697 FP64 own-GEMM "passes max|Δ|=0 vs
  cublasDgemm" — is the honest correction here: #2697 passed CORRECTNESS within fp tol (CE
  equal to 5-decimal PRINT precision), NOT bit-equality; the 17-digit CE exposes the
  nonzero delta the 5-decimal print masked.

UTIL leg — confirmed (🟢, falsifier's util condition met): the FP64 megakernel DID lift
  real-step util above eager: D1536 MEAN 9.13% → 12.57% (+3.44pp), pct>=20 13.2% → 18.5%,
  [MEGAFWD-FIRED] ≥1. So pulling the GEMMs into the cooperative launch lifts occupancy even
  in FP64 (less than P1's TF32 +5.51pp — FP64 conv is heavier per element and under-fills
  differently — but a genuine, real-step lift). CE descends identically (4.46624→3.64669,
  DESCENT=1) — the FP64-mega trains correctly.

Δ vs baseline (the finding): the byte-eq-PRESERVING util-lift is CLOSED. B3 proved
  byte-eq ⊥ util-lift under eager FP64 (megakernel can't host cuBLAS). B6 tested the
  remaining hope — that the FP64 OWN-GEMM (which DOES fit in the megakernel) could be BOTH
  byte-eq AND util-lifting — and the falsifier fires: the own-GEMM lifts util (+3.44pp) but
  is NOT byte-eq to cublasDgemm (max|Δ| 9e-16…1.8e-15 at the first forward pass). The two
  remain mutually exclusive. The ruled-out axis: "own-GEMM-in-megakernel" does not escape
  the byte-eq ⊥ util-lift wall; it only moves the precision delta from TF32-scale (~1e-3,
  P1) down to FP64-last-bit-scale (~1e-15), which is far better numerically but STILL not
  zero, so the max|Δ|=0 HARD gate stays broken. The residual — a megakernel-resident GEMM
  whose k-reduction order BIT-reproduces cublasDgemm's tiling — is the deeper
  reduction-order-reproduction problem (F-FUSION-P1B-TILED-GEMM's open frontier), a
  multi-session effort, not a wiring change.
