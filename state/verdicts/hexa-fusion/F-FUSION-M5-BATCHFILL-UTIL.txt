BATCH WIRING (done Y)
─────────────────────
  CLM_PROD_BATCH=B added to stdlib/flame/clm_prod.hexa. The trainer was strictly
  one-window-per-step (M = sequence length Tw rows for every conv GEMM). The new
  lever concatenates B distinct windows per step into one length-(B*Tw) buffer, so
  every conv GEMM's M-dimension becomes B*Tw rows (the grid grows ~linearly with B).
  ConvMoE is fully per-position (no attention); the only impurity is the K-1 causal-
  conv seam between concatenated windows — a tiny value perturbation that does NOT
  change any GEMM shape and keeps CE descending. B=1 = exact prior behavior.
  T_eff = B * Tw  (Tw = base window length = 512).
  Verified: B=1 (T_eff=512), B=4 (2048), B=8 (4096), B=16 (8192), B=32 (16384) all
  RUN (B=32 T_eff=16384 fits 80GB — NO OOM, ~5-11 GiB used, RC=0).

FINDING (closed-negative — ruled-out axis)
───────────────────────────────────────────
  🔴 FALSIFIED. Real clm_prod step util does NOT climb toward GREEN as the data batch
  grows. Across B = 1,4,8,16,32 — GEMM M-dimension 512 → 16384 rows — util MEAN stays
  PINNED at ~0.45% (B=1..16) and only inches to 0.79% at B=32, with MEDIAN 0% and
  pct>=20 ≤0.8% at EVERY batch. Growing the batch to fill the 132 SMs does NOT raise
  utilization toward GREEN; it makes each STEP proportionally slower (host-bound)
  while the device stays idle between the FP64 GEMM bursts.

  This RULES OUT batch-fill (true data-batching) as the path to util-GREEN at this
  regime — the LAST untested util lever named by M2. The wall is NOT "too few blocks
  under-fill the SMs" (M2's batch=1 hypothesis); it is the SERIAL PER-STEP STRUCTURE:
  each conv-MoE step is a chain of FP64 cuBLAS GEMMs separated by per-position glue
  (groupnorm / gelu / residual / embedding / router / col2im), and between the few
  GEMM launches the device idles regardless of how many rows each GEMM carries. A
  bigger batch just makes each GEMM taller — the GEMM still completes in a burst and
  the device returns to idle for the inter-op glue. MEAN util is the duty cycle of
  GPU-busy vs whole-step wall, and that duty cycle is invariant to batch.

  Combined with the prior HEXA-FUSION closures this EXHAUSTS the util axis:
    · M2 (#2788)  full-step megakernel +3.4pp only — fusing more does not cross GREEN
    · M3 (#2785)  bigger D — util DECLINES (GEMM-bound, host overhead scales)
    · M5 (THIS)   bigger BATCH — util FLAT ~0.45% (fill is NOT the problem)
  util-GREEN at this model/precision is unreachable by ANY sizing knob (D, batch) or by
  more cooperative fusion. The only remaining levers are the ones the campaign already
  named: a PRECISION/algorithm change that turns the serial glue+GEMM chain into one
  dense compute-bound kernel, OR a RIGHT-SIZED (smaller) GPU whose SM count the existing
  grid saturates. The util-99%-via-batch-fill question is RESOLVED: the answer is NO.

  NOTE on the measurement build: the conv GEMMs ran on the GPU (FP64 cuBLAS via
  forge_dispatch_matmul, the GEMM-FILL axis under test); the sub-ms L1/L3 fusion glue
  was host-fallback (stubbed) on this P1-runtime build — identical to the eager byte-eq
  reference path. The flat util curve is therefore the genuine eager-step duty cycle.
