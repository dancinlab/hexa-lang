PRE-REGISTERED FALSIFIER
══════════════════════════════════════════════════════════════════════════════════════
"Fusing the forward + backward kernels of the flame CLMConvMoE train step into ONE
 device graph (host off the critical path between fwd and bwd) keeps the post-step state
 (weights / grad / loss) byte-identical to the op-by-op unfused reference — max|Δ|=0
 (F-FUSION-TRAINSTEP-EQ) — AND measurably reduces per-step wall."

Two legs, each independently falsifiable:
  (g-byteeq) fused step == unfused step, max|Δ|=0 on the FP64 CE / weights / grad.
  (g-wall)   per-step wall fused < unfused (a REAL reduction, not noise).

(g-byteeq) BYTE-EQ — max|Δ| = 0 — VERBATIM
══════════════════════════════════════════════════════════════════════════════════════
The fwd+bwd fused device graph exists in TWO realizations; byte-eq splits them cleanly.

A. byte-eq-ADMISSIBLE (glue-only cooperative, GEMMs stay separate cuBLAS FP64 launches)
   — the ONLY realization that can hold max|Δ|=0. Built + fired on the REAL clm_prod_gpu
   trainer, D1536 T512, B200 (148 SM). Source: .verdicts/hexa-fusion/F-FUSION-B3-REALTRAINER.txt
   (WALL 2, reproducing F-FUSION-P2A-MEGAKERNEL.txt @ commit 09098f8cb), verbatim:

     A (megakernel OFF, op-by-op eager) : util MEAN 10.71%  PEAK 100%  pct>=20 14.3%  (n=3538)
     B (megakernel ON,  cooperative)    : util MEAN 10.63%  PEAK 100%  pct>=20 14.3%  (n=3535)
     CE byte-eq          =  PASS — A vs B BIT-IDENTICAL (epoch1 4.5471 → epoch4 3.05836, DESCENT PASS)
     [MEGAKERNEL-FIRED]  =  YES (2× cooperative, 0× under OFF = genuine, no dead-code)

   ⇒ max|Δ| = 0 (A vs B BIT-IDENTICAL, FP64 CE at full sig-digits, weights descend
   identically epoch1→epoch4). (g-byteeq) = 🟢 HOLDS for the admissible fused graph.

   WHY byte-eq holds: the fwd→bwd glue (gelu_bwd, groupnorm_bwd, expert (un)pack2,
   moe_router_bwd, grad_sum, embedding_bwd_scatter — and the fwd glue gn→gelu→resid→
   gelu2→pack→router) collapses into the cooperative kernel WITHOUT changing any float
   reduction order: every multi-element reduction (groupnorm mean/var, router softmax,
   grad_sum) stays SINGLE-THREAD SEQUENTIAL across the grid.sync barrier, and every
   conv GEMM stays the SAME cublasDgemm launch. Same ops, same order, same launches →
   bit-identical. The fusion removes only the HOST LAUNCH BOUNDARIES between glue ops.

B. byte-eq-IMPOSSIBLE (GEMM-pulling: conv GEMMs pulled INTO the cooperative kernel as
   TF32/FP64 own-GEMM tiles) — CANNOT hold max|Δ|=0 by construction. Source:
   .verdicts/hexa-fusion/F-FUSION-B6-BYTEEQ-MEGAKERNEL.txt + F-FUSION-B3-REALTRAINER.txt
   (WALL 1), verbatim conclusion:

     "you cannot get BOTH [byte-eq + util-lift] with this own-GEMM, because the FP64
      own-GEMM ≠ cublasDgemm at the bit level by construction (different k-reduction
      order). … max|Δ| ≠ 0."

   A persistent cooperative grid CANNOT nest cublasDgemm (cublasDgemm launches its own
   grid). So a fully-fused fwd+bwd graph that wants the GEMMs INSIDE the device graph
   must replace cublasDgemm with an own-GEMM whose k-accumulation order differs → the
   post-step CE deviates from the eager FP64 reference at the bit level → max|Δ| ≠ 0.
   (g-byteeq) = 🔴 FALSIFIED for the GEMM-pulling fully-fused graph. (Corroborated by
   F-FUSION-CUBLASLT-EPILOGUE-CLOSED-NEG and F-FUSION-GN-COOP-KERNEL-CLOSED-NEG: any
   multi-block parallel reduction reorders the sum → byte-eq broken.)

its glue-only realization (GEMMs stay separate cuBLAS launches; reductions single-thread)

fusion removes host launch boundaries / launch latency, which are NOT on the critical
path. This is a deterministic closed-negative, fully consistent with ④ capture/replay
(~1.0x) and W2 (0.53% MEAN): kernel-boundary fusion cannot move a glue-bound wall.
