FINDING — the value-check caught its own naive wide-constant assumption first
──────────────────────────────────────────────────────────────────────────────
The first guard run (before this fix) FAILED on `0xdeadbeef` with
"FAIL immediate #0xdeadbeef MISSING (literal re-collapsed?)" → GUARD_RC=1. This
was NOT a codegen regression. Inspection of the emitted object showed the
constant is correctly lowered as a two-instruction MOVZ/MOVK pair:

  0000000000000084  mov  x1, #0xbeef
  0000000000000088  movk x1, #0xdead, lsl #16

i.e. 0xdeadbeef = 0xdead<<16 | 0xbeef = 3735928559. A 32-bit constant cannot
fit a single arm64 `mov #imm16`, so the backend emits the low 16-bit half via
MOVZ and the high half via MOVK — the full `#0xdeadbeef` token never appears in
the disassembly. The hex-literal fix (#47421c89c) is intact: both 16-bit halves
are present, and a regression to #0x0 would drop both chunks. The guard's
value-check was corrected to assert the 16-bit chunk decomposition for
wide constants (>16 bits check #0xbeef AND #0xdead) rather than the
never-emitted full immediate. This is a honest g63 catch — the guard rejected a
false negative in its own assertion logic before being declared green.
