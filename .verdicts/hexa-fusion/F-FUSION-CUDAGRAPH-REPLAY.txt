═══ ROOT CAUSE — why the proven ≥30% (⑧) does NOT transfer here (honest g5) ════════
  The ⑧ launch-amort proof (n*=-26595, ≥30% UNCONDITIONAL) is about a PURE kernel
  sub-graph where the per-step host cost = N cudaLaunch calls (~5-10µs each) and HBM
  traffic — there the graph collapsing N launches → 1 cudaGraphLaunch is a real ≥30%
  win. But the flame CLMConvMoE train step's per-step host critical path is dominated
  NOT by kernel-launch latency but by INTERPRETED HOST GLUE that the graph CANNOT
  capture:
    (a) the per-window token copy (T× t_get/t_set host scalar loop) at the loop head;
    (b) the 28-call AdamW optimizer sweep — kept EAGER (host bias-correction t), each
        a host-driven forge_dispatch with a host round-trip;
    (c) the eager metric steps (first+last nwin loss readback, host d2h);
    (d) the residual interpreted inter-op glue between device GEMM spikes.
  The captured fwd→bwd kernel ISSUE is a tiny slice of per-step wall, so amortizing its
  launch overhead with cudaGraphLaunch moves the needle ~0. As D/T grow the per-kernel
  GEMM time grows (roofline / cuBLAS Dgemm dominates) and the launch slice shrinks
  FURTHER toward irrelevance — there is no launch-bound knee to exploit because the host
  bound here is the interpreter, not the driver. This is the SAME wall the prior
  util-only verdicts hit (F-FUSION-GRAPH-AB +1.32pp util; -WHOLESTEP-AB +0.35pp more),
  now quantified on the PER-STEP WALL axis: the graph's wall benefit is ~0 because
  graph capture amortizes cudaLaunch, and cudaLaunch is not this step's bottleneck.
