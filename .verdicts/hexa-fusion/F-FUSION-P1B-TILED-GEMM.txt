F-FUSION-P1B-TILED-GEMM — HEXA-FUSION Phase 1b: shared-memory TILED FP32 own-GEMM
================================================================================
Goal: close the measured 7.6x naive-vs-cuBLAS gap from Phase 1d (the naive
one-thread-per-output _hx_k_sgemm_cm) with a shared-memory tiled kernel
(HXTILE=16), faithful to cublasSgemm (same col-major signature/semantics +
transpose handling). cuBLAS = correctness ORACLE (fp32 tolerance, NOT bit-exact
— accumulation order differs). g5-HONEST: measured numbers VERBATIM; the tiled
kernel is markedly faster than naive (shared-mem reuse) but does NOT match
cuBLAS (no Tensor-Cores, basic single-stage tile) — reported as the remaining gap.

WHAT WAS AUTHORED (Phase 1b, env-gated HEXA_OWN_GEMM_TILED; reuses the p1d driver)
---------------------------------------------------------------------------------
- self/native/hxqwen14b_cuda.cu (nvcc TU): a NEW shared-memory tiled kernel
    __global__ _hx_k_sgemm_cm_tiled(tA,tB,M,N,K,alpha,A,lda,B,ldb,beta,C,ldc)
    — SAME col-major signature/semantics + transpose handling as the naive
    _hx_k_sgemm_cm_v54. HXTILE=16: each 16x16 block cooperatively stages a
    16x16 sub-tile of op(A) and op(B) into __shared__ As/Bs, __syncthreads,
    accumulates over the tile, __syncthreads, advances over K. Each global
    element loaded once per tile is reused HXTILE times from shared memory.
- Wired into the SAME extern "C" launcher _hx_own_sgemm_cm_launch: when env
    HEXA_OWN_GEMM_TILED is set+non-empty it launches the tiled kernel (with a
    once-per-process [OWN-SGEMM-TILED-FIRED] stderr probe), else the existing
    naive kernel. grid=((M+15)/16,(N+15)/16), block=(16,16).
  Gate nesting: the OUTER HEXA_OWN_GEMM gates own-vs-cuBLAS (the p1d shims,
    unchanged); HEXA_OWN_GEMM_TILED selects tiled-vs-naive WITHIN the own path.
    Neither set => cuBLAS, byte-identical to before.
- Correctness/perf driver REUSED verbatim from p1d (hxqwen14b_p1d_driver.cu):
    drives hxqwen14b_lora_fwd_single + _bwd_single on device, dumps y/dA/dB/dx,
    optional CUDA-event timed loop (P1D_ITERS). New rel-RMS cmp (p1b_cmp.c).

PERF — 3-WAY ms/iter (GEMM-BOUND M=N=K=2048 R=16, fwd+bwd LoRA, CUDA-event, 50 iters)
------------------------------------------------------------------------------------
  cuBLAS (oracle):  7.1453 ms / 50 = 0.14291 ms/iter
  naive  (own):    55.3373 ms / 50 = 1.10675 ms/iter
  tiled  (own):    44.6290 ms / 50 = 0.89258 ms/iter

RATIOS (verbatim arithmetic):
  naive -> tiled  speedup = 1.10675 / 0.89258 = 1.24x  (tiled is 1.24x FASTER than naive)
  tiled  vs cuBLAS gap    = 0.89258 / 0.14291 = 6.25x  (tiled still 6.25x SLOWER than cuBLAS)
  naive  vs cuBLAS gap    = 1.10675 / 0.14291 = 7.74x  (matches p1d's ~7.6x baseline)
  => the tiled kernel closed the naive-vs-cuBLAS gap from 7.74x to 6.25x
     (a 1.24x step toward cuBLAS via shared-memory reuse).

OUTCOME (g5-HONEST)
-------------------
- TILED-FIRED: YES (1x under the tiled arm, both shapes; 0x oracle/naive arms).
- CORRECTNESS: PASS — TILED vs cuBLAS rel-RMS ~1e-6 on y/dA/dB/dx, within fp32 tol.
- PERF: tiled 1.24x faster than naive (0.89258 vs 1.10675 ms/iter), closing the
  naive->cuBLAS gap from 7.74x to 6.25x. The win is REAL but MODEST — a basic
  single-stage 16x16 shared-mem tile cuts global-memory traffic (each load reused
  16x) but does NOT touch the FP32 CUDA-core compute ceiling: no Tensor-Cores, no
  register-blocking (each thread still computes one output), no double-buffered
  k-loop / vectorized loads. So it stays 6.25x off cuBLAS's TC-tiled Sgemm. This
  is the honest measured result, NOT a "matched cuBLAS" claim.
- NEXT (Phase 1b deeper, gap-driven): register-tiling (e.g. 64x64 block tile with
  an 8x8 per-thread micro-tile + double-buffered shared loads) is the standard way
  to lift FP32-CUDA-core GEMM from ~memory-bound toward compute-bound; Tensor-Core
  (TF32/BF16 WMMA) is the path to actually approach cuBLAS but changes dtype/accuracy.
