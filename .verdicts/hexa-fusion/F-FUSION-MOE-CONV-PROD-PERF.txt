  Falsifier (pre-registered): "cp.async multi-stage prefetch hides the per-chunk
  Xs+Ws HBM load latency the OG-FUSE-OPT verdict pinned, closing E→cuBLAS."
  FALSIFIED — path G is slower at every measured d, byte-eq held.

  Mechanism (deterministic ruling-out): the GEMM-conv K-loop uses GM_BK=16, so
  d/16 = up to 388 chunks. Per chunk the cp.async pipeline pays commit_group +
  wait_group + an extra __syncthreads, while the per-chunk compute (16 ci × K=3
  over a 4×4 register tile) is tiny → async-pipeline bookkeeping > the latency it
  hides. Path E already overlaps loads via OCCUPANCY (many CTAs/SM, the warp
  scheduler hides global latency), so explicit cp.async prefetch adds overhead
  without adding overlap. The OG-FUSE-OPT-pinned wall is L2/WEIGHT BANDWIDTH (each
  weight byte amortised BM=64-fold but still streamed once from HBM), which is a
  BANDWIDTH bound — cp.async addresses LATENCY, not bandwidth, so it structurally
  cannot move this wall. (Forced GM_STAGES 3→2: the 3-stage static __shared__
  ring = 49536 B exceeds the 48KB/49152 B per-block STATIC smem hard cap and the
  launch failed with cudaErrorInvalidValue; 2-stage = 33024 B fits. A deeper ring
  is impossible in static smem and dynamic smem would not change the bandwidth
  conclusion.)

  Ruled-out axis: latency-hiding (cp.async / multi-stage prefetch) is NOT the
  lever for this kernel. Path E at 6.58x / 15.7x-from-roofline is at its design
  ceiling on the LATENCY axis. The remaining gap to cuBLAS is BANDWIDTH +
  arithmetic-intensity: cuBLAS reuses each weight tile across a far larger output
  tile (higher AI) AND uses wgmma. Closing it requires raising arithmetic
  intensity (wider BM/BN register or wgmma tiles — lever c / b), NOT prefetch.
