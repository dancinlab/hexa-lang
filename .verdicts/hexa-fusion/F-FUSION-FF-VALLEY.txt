WHAT WAS BUILT
  Two persistent grid-synced glue kernels (env-gated HEXA_FUSE_VALLEY) that fuse ONLY the
  between-GEMM valley and keep the 4 own-GEMM convs as SEPARATE (already-saturated) launches —
  the valley-only distinction vs the closed-negative WHOLE-fwd megakernel (_hx_k_clm_megafwd_fp64,
  which pulls the GEMMs inside the one-wave coop grid and de-saturates them):
    _hx_k_clm_valley1_fp64  (VALLEY-A): groupnorm#1 -> gelu -> residual (xt = xec + gelu(hn0))
    _hx_k_clm_valley2_fp64  (VALLEY-B): gelu2 + expert-pack + moe-router(softmax+combine) -> groupnorm#2
  + coop launchers _hx_cuda_farr_clm_valley{1,2}_gpu (one-wave grid, grid.sync legal; -1 fallback
    to eager separate-kernel glue on no-coop), C wrappers forge_dispatch_clm_valley{1,2}.
  Reuses the IDENTICAL byte-eq device fns the GREEN L3 chain / whole-megakernel already proved:
  _hx_dev_groupnorm (host-order t-outer/c-inner reduction, NR-40 _hx_gn_sqrt_dev), _hx_gelu_dev
  (erf, 1/sqrt2 literal), _hx_moe_exp_dev (scaled-Taylor). The valley DAG splits into 2 kernels
  because the 2 expert GEMMs sit between block-1 and block-2 (a single persistent kernel can't
  span them without re-including those GEMMs — that would be the whole-megakernel again).

UTIL before/after (nvidia-smi, sustained fused run T=256 D=1024):
    fused persistent kernel: utilization.gpu = 100% (8/8 samples).
  HONEST: this 100% is the COARSE nvidia-smi any-SM-busy flag — the resident persistent grid
  keeps a block busy-waiting at the grid barrier on every SM, so it reads 100% even though the
  byte-eq-forced GN reduction is SINGLE-THREAD (thread-0 only). It is NOT a compute-occupancy
  gain. This is exactly the F-FUSION-OCCUPANCY-WALL caveat: byte-eq FORCES the reduction serial,
  so the persistent kernel buys ZERO reduction-parallelism. The real win here is WALL-TIME of the
  valley (2.5x: collapsing per-op launches + overlapping the 2 GN single-thread reductions with
  the parallel normalize/gelu passes inside one resident grid), NOT SM saturation.

  ⚠ HONEST CAVEAT (the load-bearing finding): the ~99% valley fraction is an ARTIFACT of the
  byte-eq-forced SINGLE-THREAD GN reduction (an O(T*D) serial loop on one thread dominates the
  FP64 step). It is NOT a real-workload property. In a non-byte-eq trainer the GN would be a
  PARALLEL reduction (~microseconds) and the valley fraction would collapse to a few %, putting
  the step-level lever back near the MPK 1.2–1.3x cross-task-pipelining ceiling the milestone cited.
  So: FF-VALLEY's 2.5x is REAL and byte-eq-GREEN for the FP64 byte-eq path as built, but it is the
  step-level Amdahl lever ONLY because byte-eq makes the valley pathologically dominant; it does
  NOT generalize to a parallel-reduction trainer. The structural lever (persistent valley fusion,
  GEMMs left saturated) is VALIDATED and byte-exact; the magnitude is byte-eq-regime-specific.
