═══ THE WALL (honest root cause — why the A/B is NOT a fusion test) ═══
A one-shot stderr marker was inserted in the wrapper at the device-launch line
  (`[L3A-FIRED] groupnorm_gelu DEVICE path taken`), relinked, and probed under FUSE=1.
  RESULT: marker fired 0 times. NO cuda error. → the device fused kernel is NEVER invoked.

ROOT CAUSE: the fused entry `nn_gn_gelu_fused` (gn_lib.hexa:379) is DEAD CODE in the
  production path. In the transpiled clm_prod.c it has exactly 2 occurrences (1 proto +
  1 definition) and ZERO call sites. The CLM forward loop (clm_prod.hexa:470) calls the
  SEPARATE `nn_groupnorm_fwd` (plain GN) and applies GELU downstream — it does NOT route
  through `nn_gn_gelu_fused`. The gate inside `nn_gn_gelu_fused_off`
  (env HEXA_FUSE_GN_GELU && DEVRESIDENT && goff==0 && boff==0 → forge_dispatch_groupnorm_gelu)
  is therefore never reached. Both FUSE arms run the IDENTICAL unchanged eager host/GN path,
  which is why CE is byte-identical and util is flat — that is an ARTIFACT of the call-site
  gap, NOT evidence the GN→GELU fusion lever raises or fails to raise util.
