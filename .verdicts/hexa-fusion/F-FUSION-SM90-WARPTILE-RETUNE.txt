FINDING (CLOSED-NEGATIVE — the occupancy axis is deterministically ruled out):
  Doubling occupancy (1 → 2 blocks/SM via a 46% register cut) did NOT raise own throughput — it
  REGRESSED slightly (11.1 → 10.7 TFLOP/s, -4%) and the cuBLAS gap WIDENED (31.4× → 32.5×). Reproduced
  across 2 independent runs (stable, not noise). Therefore register pressure / SM occupancy is NOT the
  binding constraint on the WMMA2 own-GEMM. The kernel is bound by its inner-loop MATH PIPELINE, not by
  block count: per-element __float_to_tf32 software rounding on every fragment load, a depth-1 cp.async
  prefetch (no deep multi-stage pipeline), a scalar shared-staged epilogue, and no register-blocked
  double-buffered mainloop. Adding a second resident block cannot hide that latency when one block
  already under-utilizes the tensor cores; it adds scheduling pressure (and the spill) instead.
  % of the 29.5× (here 31.4×) gap closed by the register-reduction axis: 0% (negative).
  PARITY: N (own-GEMM remains ~31× off cuBLAS on native sm_90; this attempt did not move it).

RULED-OUT SPACE: "WMMA2 own-GEMM is occupancy/register-bound on sm_90" is FALSE. Closing the gap is NOT
a register-pressure problem — it requires a cuBLAS-class TC mainloop rework (deep cp.async pipelining,
ldmatrix/mma.sync without per-element software TF32 rounding, register-blocked accumulation, vectorized
epilogue), i.e. effectively reimplementing the CUTLASS-grade inner loop. That is a multi-session pipeline
rewrite, not a one-knob retune. HONEST framing: this is parity-seeking, no superiority claim; the RR
variant ships env-gated + default-OFF (parent path byte-identical) as a verified negative datapoint.
