DIAGNOSED BOTTLENECK (measured, not just analyzed):
  (1) SKINNY-GEMM TILE WASTE = the dominant cause. The two SQUARE GEMMs (fwd_y, bwd_dx)
      are already FASTER than cuBLAS under WMMA2 (0.15 vs 0.22/0.20 ms). The ENTIRE gap is
      the 5 skinny GEMMs where the 128x64x32 WMMA2 tile is launched over a 16-tall (or
      16-wide) output -> >=75% of every threadblock + half the BK K-tile wasted. cuBLAS
      handles skinny shapes well (0.10-0.12 ms); the big-tile WMMA2 is the WRONG TOOL for a
      skinny GEMM (3.8x-7.8x slower). 5x0.12 ms (cuBLAS) -> 5x ~0.5 ms (WMMA2) IS the gap.
  (2) PER-CALL cudaDeviceSynchronize() in _hx_own_sgemm_cm_launch serialized all 7 GEMMs +
      glue every step (7 host<->device round-trips/step the async cuBLAS arm never pays).
      Secondary on THIS workload (each skinny GEMM is heavy so launch latency is small vs
      GEMM time) but a real cost (+~12 steps/s alone @M8192).

  HONEST: the skinny LoRA GEMMs ARE somewhat TC-unfriendly (tiny output dim wastes the
  TC tile), but they are NOT fundamentally unfixable — the fix is to NOT use the big TC
  tile on them. A right-sized small-tile (16x16 shared) path recovers most of the loss.

========================================================================================
§2  TUNE APPLIED (self/native/hxqwen14b_cuda.cu, _hx_own_sgemm_cm_launch)
========================================================================================
(a) DROP the per-call cudaDeviceSynchronize() -> non-blocking cudaGetLastError() launch
    check. The 7 GEMMs + glue now queue async like cuBLAS; the caller syncs once at the
    step boundary (the glue/CE readback already does). Env HEXA_OWN_GEMM_SYNC=1 restores
    the old per-call sync for debugging.
(b) SHAPE-DISPATCH: a "skinny" GEMM (output m<HXG_BM=128 OR n<HXG_BN=64 — i.e. every R=16
    LoRA GEMM) falls back to the 16x16 shared-mem tiled kernel (_hx_k_sgemm_cm_tiled),
    which launches a right-sized grid with NO wasted 128x64 tile. Only the big SQUARE
    GEMMs use WMMA2 (where it is already >= cuBLAS). Env HEXA_OWN_GEMM_NOSHAPE=1 disables.
    Skinny-fallback choice MEASURED: tiled (16x16) beats naive one-thread-per-output
    (337 vs 240 steps/s @M8192) because K is large (4096-8192) so shared-mem K-reuse wins
    even with a half-wasted 16-wide M tile. Env HEXA_OWN_GEMM_SKINNY_NAIVE=1 = naive (slower).
All gates: env-gated, OFF (default cuBLAS) = byte-identical. Correctness contract unchanged.

WMMA2-TUNED per-GEMM (pergemm, same shapes): SUM 7-GEMM 3.22 -> 2.15 ms (skinny GEMMs
  drop: dA 0.94->0.44, dB 0.69->0.43, tmp/u 0.43->0.33). Still 2-4x off cuBLAS on skinny
  (the simple 16x16 tiled kernel is not split-K; cuBLAS uses split-K on tiny-output/large-K)
  -> a residual gap remains; see §5 honest scope.

========================================================================================
§5  FINDING (honest scope)
========================================================================================
DIAGNOSED: the 2.2x full-step steps/s gap (despite 1.13x GEMM-iso) is NOT the dense GEMM
throughput — it is the 5 SKINNY R=16 LoRA GEMMs, where the 128x64 WMMA2 tile wastes >=75%
of every threadblock (output dim = R = 16). The 2 SQUARE GEMMs are already faster than
cuBLAS under WMMA2. A per-call cudaDeviceSynchronize was a secondary serializer.

TUNED: shape-dispatch skinny->16x16 tiled + drop per-call sync. Gap 2.24x -> 1.67x @M8192
(2.14x -> 1.59x @M16384) = ~46-48% of the gap closed, correctness PASS (rel-RMS <= 3e-4,
CE descent bit-identical), zero default behavior change (env-gated).

NOT FULL PARITY (honest): WMMA2-tuned is still ~1.6-1.7x slower steps/s. The residual is
the skinny GEMMs themselves: cuBLAS runs SPLIT-K on tiny-output/large-K GEMMs (dA/dB have
output 16 with K=8192) — our 16x16 tiled kernel does a single sequential K-reduction per
output, so it cannot match cuBLAS on these shapes. Closing the last ~0.6x would need a
split-K (or stream-K) skinny kernel — a real but separable kernel-engineering step, not
a tuning knob. The brief's "small-tile / non-TC path for skinny GEMMs" diagnosis is
CONFIRMED CORRECT and is exactly what closed ~half the gap; the rest needs split-K.

VERDICT: 🟢 ~46-48% of the 2.2x throughput gap CLOSED, byte-eq/TF32-correct, root cause
diagnosed and measured. Residual gap = skinny-GEMM split-K (named, not closed).
