    round). Faithful col-major cublasGemmEx(CUDA_R_16BF): C[i+j·ldc] = α·Σ op(A)·op(B) + β·C.

═══ §FINDING ═══
(1) CORRECTNESS — GREEN. A hexa-native BF16 WMMA own-GEMM matches cuBLAS-BF16 to rel-RMS 0.000e+00
    (≤ 1e-2 BF16 tol), across square (2048³, 4096³) and odd bounds-guard (130×70×96) shapes. We now own a
    BF16 own-GEMM that is numerically faithful to the cublasGemmEx(CUDA_R_16BF) contract — adding the
    BF16 dtype to the FP32 (WMMA2 TF32) + FP64 (clm) own-GEMM coverage. [FIRED] confirmed; OFF is the
    byte-identical default.

(2) PRECISION TRADEOFF (named explicitly, per the BF16 bar). BF16-own's error vs fp64 is 2.09e-3 — the
    bf16 ~8-bit-mantissa floor, ~8× looser than the TF32 path (2.6e-4). This is a PRECISION CHANGE, not
    a free speedup: usable on the INFERENCE / FORWARD path (logits, FFN/MLP, attention QKV·O projections
    — bf16 is the industry-standard activation dtype there). It is NOT a drop-in for precision-critical
    fp32-accumulation paths (e.g. small-Δ optimizer/grad-accumulation or ill-conditioned reductions)
    without an error-budget check. We do NOT claim fp32-grade precision.

(3) THROUGHPUT — CLOSED-NEGATIVE (the falsified clause, honestly reported). BF16-own does NOT approach
    cuBLAS-BF16: it sustains only 13-17 TFLOP/s vs cuBLAS-BF16's 1021-1424 TFLOP/s (~77-85× slower),
    and is actually slower than even FP64-cuBLAS in absolute TFLOP/s. The 128×64 WMMA2-mirrored schedule
    that reached cuBLAS-CLASS util in the TF32 path does NOT transfer to BF16 here: the binding cost is
    the staging pipeline — fp32→bf16 must be ROUNDED on a thread before the shared store (cp.async cannot
    cast fp32→bf16 in-flight), so the BF16 path lost the TF32 path's true cp.async double-buffer overlap
    (the prefetch degenerates to plain blocking bf16 stores + a per-element scalar __float2bfloat16 of
    24 elems/thread/K-slice). The result is a correct-but-memory/stage-bound kernel, NOT a TC-peak one.
    → A clean kernel optimization (a real cp.async-staged bf16 double buffer that hides the fp32→bf16
      round, or accepting pre-rounded bf16 device buffers so cp.async applies) is the named next step;
      it is OUT OF SCOPE for C1's "author + correctness-prove the BF16 own-GEMM" milestone.

(4) DTYPE-AXIS (the axis the README's 9.67× is about) — CONFIRMED at the cuBLAS level. The bf16-vs-fp32-
    vs-fp64 throughput ordering IS real and large: cuBLAS-BF16 is 29-40× FP64-cuBLAS and 1.65-1.89×
    FP32-cuBLAS(TF32). So the dtype speedup the README headline cites (9.67× over FP64-cuBLAS) is
    directionally validated by the cuBLAS reference here (cuBLAS-BF16 vs FP64-cuBLAS = 29-40×). The
    finding is that OUR own BF16 kernel does not yet REALIZE that axis (it's correct but slow); the axis
    itself is confirmed, the own-kernel realization is the open residual.

NO perf claim is made beyond the measured numbers; the correctness gate (rel-RMS ≤ 1e-2) PASSED before
any throughput statement. This is NOT a "surpass cuBLAS" result. Pod destroyed (leak 0).
