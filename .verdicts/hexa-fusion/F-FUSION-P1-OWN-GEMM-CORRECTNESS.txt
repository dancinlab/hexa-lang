═══ THE IMPLEMENTATION (Phase 1a + 1c, in self/cuda/runtime_cuda_emit.hexa) ═══
- Phase 1a __global__ _hx_k_gemm(A,B,C, M,K,N): row-major C[M,N]=A[M,K]·B[K,N], one thread per output
  (m,n), naive sequential K-accumulation. Env-gated inside _hx_cuda_farr_matmul_gpu: HEXA_OWN_GEMM set →
  16×16-block launch of _hx_k_gemm on _forge_stream(); OFF → cublasDgemm UNCHANGED. One-shot
  "[OWN-GEMM-FIRED] _hx_k_gemm DEVICE path (no cuBLAS)" stderr marker at the device launch.
- Phase 1c __global__ _hx_k_gemm_strided_batched(A,B,C, M,K,N,batch): per-batch row-major GEMM, one
  thread per (b,m,n), naive K-accum. Env-gated inside _hx_cuda_farr_matmul_batched_gpu (the conv2 expert
  path): HEXA_OWN_GEMM set → 3D grid (N,M,batch) launch; OFF → cublasDgemmStridedBatched UNCHANGED.
  One-shot "[OWN-GEMM-FIRED] _hx_k_gemm_strided_batched DEVICE path (no cuBLAS)" marker.
- cuBLAS stays LINKED (the OFF path + the oracle arm use it). NOT bit-identical to cuBLAS by design
  (own naive k-accum order ≠ cuBLAS tiling order) — cuBLAS is DEMOTED to a correctness ORACLE here.

═══ FINDING ═══
1. [OWN-GEMM-FIRED] = YES for BOTH kernels (single + strided-batched) under HEXA_OWN_GEMM=1, 0× under
   the oracle arm. The own path genuinely ran — numbers are valid (not dead-code).
2. CORRECTNESS = PASS. max|Δ CE| = 0.00000 at the printed 5-decimal precision (the clm_prod harness
   prints only epoch-1 and epoch-4 mean CE). Both arms 4.46624 → 3.64669. This is INSIDE the ~1e-6
   relative tolerance bar (in fact the displayed values coincide to all printed digits). CE descends
   in both arms (DESCENT=1). The own naive-k-accum GEMM trains the model correctly vs the cuBLAS oracle.
   NOTE (g5 honest): the harness rounds to 5 decimals, so the true max|Δ| could be nonzero below 1e-5
   but is bounded by < 5e-6 absolute on CE≈3.65–4.47 (< ~1.4e-6 relative) — comfortably within bar.
3. STEP-TIME ratio (own/cuBLAS) = wall_B/wall_A = 223.1 / 244.4 = 0.913 (own ~8.7% FASTER wall here).
   HONEST INTERPRETATION (NOT a perf-win claim): the naive O(MKN) one-elem-per-thread own GEMM is
   expected to be SLOWER than cuBLAS in raw GEMM FLOPS. It was not slower at the WALL because this
   workload is LAUNCH-BOUND, not GEMM-compute-bound (median GPU util = 0% in both arms; the campaign's
   established profile is host-launch / per-op dispatch on the critical path, small FP64 GEMMs @ D1536
   under-filling the H100). GEMM compute time is hidden behind host launch latency, and the ~9% wall
   gap is within run-to-run variance for a launch-bound 4-epoch step. So: no slowdown OBSERVED at this
   size, but DO NOT read a speedup — the real GEMM-FLOPS gap will surface once Phase 1b tiling removes
   the launch wall and/or on a GEMM-bound (large-batch / LLM) workload. This is exactly the gap-data
   Phase 1b needs.
