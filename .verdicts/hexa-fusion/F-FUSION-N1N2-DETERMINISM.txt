N2 — THE ~1e-1 SOURCE (kernel + buffer + mechanism)  ·  PINNED
════════════════════════════════════════════════════════════════════════════════
Real clm_prod device-eager glue, own-GEMM, EPOCHS=1, D1536 T512, first_ce ×3 (verbatim):

  PRE-FIX:
   ASYNC-ON  racefix OFF: 4.8704863554368121 / 4.9160238631363509 / 4.9126752530410958  (spread ~4.6e-2)
   ASYNC-ON  racefix ON : 4.9160238631363509 / 4.9160238631363509 / 4.9122580866412253  (spread ~3.8e-2)
   ASYNC-OFF (HEXA_CUDA_ASYNC=0): 4.4662394504526679 / 4.4662394504526679 / 4.4662394504526679  (Δ=0)

MECHANISM = an ASYNC-PIPELINE CROSS-STREAM RACE on the device-resident chain.
_forge_async_on() (auto-ON under CLM_PROD_DEVRESIDENT) launches the glue kernels
on a cudaStreamNonBlocking g_forge_stream with NO per-launch host sync. But the
buffer-management ops — _h2d's cudaMemcpy H2D, _ensure_dev_alloc_out's
cudaFree/cudaMalloc/cudaMemset, the GEMM-C realloc/memset (the conv own-GEMM) —
run on the DEFAULT stream. A cudaStreamNonBlocking stream is NOT ordered against
the default stream, so a default-stream buffer op (free / malloc / memcpy / memset)
RACES a still-queued forge-stream kernel reading/writing that buffer → the
~4.6e-2 run-to-run jitter. _d2h already drains the forge stream (_forge_sync)
before its D2H; the H2D / alloc / GEMM-C paths did NOT.

  PROOF: HEXA_CUDA_ASYNC=0 (collapse onto the default stream, every launch synced)
  is BIT-REPRODUCIBLE (4.4662394504526679 across every run, every build) while
  ASYNC-ON jitters. The race is on the async kernel-launch pipeline, full stop.
  The buffer carrying it = any device-resident intermediate whose default-stream
  re-management (alloc/free/memset/H2D) overlaps a queued forge-stream kernel.

HONEST: the targeted _forge_sync drains REDUCE the jitter (most runs now hit the
correct 4.9147686043046424) but do NOT fully eliminate it — the async pipeline has
ADDITIONAL default-stream device ops (e.g. _d2h_out, copy_slice, the attn-P memset,
elementwise D2H, zero_slice) that are each a latent cross-stream hazard. A
whack-a-mole of per-site _forge_sync drains does not converge; the residual race
recurs intermittently. The ARCHITECTURAL fix (single ordered stream for the WHOLE
device-resident chain, OR route every buffer op onto g_forge_stream) is the proper
closure and is left as the follow-up — it is a runtime-design change beyond a
minimal patch.
