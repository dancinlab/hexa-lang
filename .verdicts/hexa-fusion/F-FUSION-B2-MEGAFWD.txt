The 11-phase fwd DAG chained in ONE cooperative launch (8 grid.sync() barriers):
  PHASE 0   H1 = A·W1                              (conv GEMM1, own-GEMM WMMA2 inline)
  --grid.sync--
  PHASE 1a  per-row mean/var of H1                 (groupnorm reduction — CROSS-BLOCK)
  --grid.sync--   (the cross-block reduction the megakernel design names as the unblock)
  PHASE 1b  N = groupnorm(H1)                       (normalize using the reduced stats)
  PHASE 1c  E = gelu(N)                             (glue block-1)
  PHASE 1d  R = E + H1                              (residual add — fused into 1c)
  --grid.sync--
  PHASE 2   H2 = R·W2                               (conv GEMM2, own-GEMM WMMA2 inline)
  --grid.sync--
  PHASE 3a  G2 = gelu(H2)                           (glue block-2, gelu2)
  PHASE 3b  P  = expert_pack(G2)                    (per-row gated pack — fused into 3a)
  --grid.sync--
  PHASE 3c  per-row max+sumexp of P                 (moe_router softmax reduction — CROSS-BLOCK)
  --grid.sync--
  PHASE 3d  Rt = softmax(P)                         (moe_router normalize → FINAL out)
Intermediates H1/N/R/H2/P + the per-row stats live in DEVICE scratch across every
barrier — no host round-trip, no relaunch. The gn + router reductions are genuine
CROSS-BLOCK reductions: pass-1 writes per-row stats to global, grid.sync() makes
them globally visible, pass-2 reads them — realized with the SAME grid.sync().
Eager reference = the SAME 8 ops as 8 SEPARATE launches (the serial per-kernel-sync
DAG that H1a/H1b name as the util wall). Both paths use the identical TF32 own-GEMM
kernel + identical fp32 glue → bar = rel-RMS <= 3e-3.

────────────────────────────────────────────────────────────────────────────────
BUDGET WALL ENCOUNTERED + RESOLVED  (the honest engineering finding)
────────────────────────────────────────────────────────────────────────────────
On sm_100 (B200) the per-block STATIC shared cap is 49152 B (0xc000). The shipped
WMMA2 own-GEMM uses As(32768)+Bs(16384)+tmp(8192 epilogue) = 57344 B static — OVER
the cap; nvlink rejected BOTH the standalone GEMM and the megakernel. Resolved with
two PLACEMENT-ONLY (math byte-identical) changes, NOT algorithm changes:
  (1) alias the GEMM epilogue `tmp` onto `As` (dead during the epilogue) → 49152 B.
  (2) the megafwd declares ONE function-scope 49152 B shared buffer reused by ALL
      phases (GEMM As/Bs/tmp AND the gn/router warp-shuffle reduction staging) —
      no two phases live at once (grid.sync separates them), so a single allocation
      pins total static shared at EXACTLY the cap. A second static buffer (even 64 B)
      pushed it to 0xc040 > cap and nvlink rejected the cooperative launch.
  Plus: gn/router reductions use WARP-SHUFFLE (32 B) not 256-float __shared__ buffers.
Net: the FULL fwd FITS one cooperative launch — megafwd kernel = 246 registers,
49152 B smem (exactly the cap), occ = 1 block/SM × 148 SM = 148 co-resident blocks
(occupancy query: no error). NO prefix-truncation needed: the WHOLE fwd fits.

WHY (diagnostic, same mechanism H1b documented, now confirmed on the FULL fwd):
  Even the FULL fwd at these shapes is GEMM-DOMINATED on a B200 — both paths already
  sit at 92-95% util (near-saturated). The sub-ms glue (gn/gelu/resid/pack/router) the
  megakernel is designed to gap-collapse is a SMALL fraction of each fwd step's wall vs
  the two conv GEMMs, AND the eager path's 8 launches PIPELINE on one stream (the async
  launch queue hides the host-side launch gaps under the running GEMMs). So there is no
  idle for the megakernel to reclaim. The megakernel is also consistently SLOWER because
  a single FIXED 148-block cooperative grid must STRIDE over two differently-shaped GEMMs
  + serialize the per-row gn/router reductions across only 148 blocks for M rows, whereas
  eager launches each phase with a right-sized grid; the grid.sync() barriers add real
  cost. This REGRESSION grows with GEMM size (-4.4% at 128⁴ → -9.4% at 1024×1536),
  confirming the GEMM-schedule-efficiency loss, not a glue effect.

  => The util-raising payoff the megakernel targets requires a regime where the sub-ms
     glue actually DOMINATES the step wall and the GPU genuinely idles between launches
     (the F-FUSION-OCCUPANCY-WALL median-2% regime — many tiny HETEROGENEOUS kernels with
     real inter-launch host stalls). A B200 running back-to-back conv-block fwds at D∈
     [128,1536] does NOT idle: the GEMMs fill it and the launch queue hides the gaps. On
     THIS workload the cooperative-megakernel STRUCTURE is fully realized (full fwd, one
     launch, byte-exact, co-resident) but the gap-collapse has nothing to reclaim and the
     fixed-grid striding COSTS throughput. Honest: structure ✓ (full fwd, fits, byte-exact);
