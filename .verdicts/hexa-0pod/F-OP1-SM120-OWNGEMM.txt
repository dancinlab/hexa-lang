F-OP1-SM120-OWNGEMM — sm_120 own-GEMM speedup on aiden (RTX 5070, cc12.0), bit-exact
=====================================================================================
STATUS: GREEN — best bit-exact config = K2 (pad + .v4 + cp.async double-buffer).
HARDWARE: aiden RTX 5070 (sm_120 / cc12.0), CUDA 13.0, free sidecar pool (no vast).

GOAL: improve OWN120 (mma.sync.aligned.m16n8k8.row.col.f32.tf32.tf32.f32, 64x64
block, BK=16) throughput toward consumer-card cuBLAS-TF32, staying bit-exact
(rel-RMS vs K0 baseline == 0, bitdiff == 0 — scheduling/layout-only changes, NOT
accumulation-order changes; nonzero = bug, rejected).

BASELINE (F-BENCH-5 #2943): OWN120 ~4.9-8.1 TFLOP/s, 3.2-6.9x off cuBLAS-TF32.
This sweep's K0 (== that baseline) re-measured on aiden: 6.75 TFLOP/s @1024 (4.16x
off), 8.05 TFLOP/s @2048 (3.83x off).

KERNEL VARIANTS (self/native/mma_sm120/owngemm_sm120_opt.cu, sweep harness):
  K0 = baseline (64x64, BK=16, scalar smem load, no pipeline)              [ref]
  K1 = +bank-conflict-free smem pad (As[BM][BK+4], Bs[BK][BN+4]) + .v4      (lever 2,5)
       (128-bit float4) global loads
  K2 = K1 + cp.async double-buffered BK stage (deeper pipeline)            (lever 1)
  K3 = larger per-CTA register tile 128x64 (8 warps, raise AI)             (lever 3)
  K4 = K3 + cp.async double-buffer + pad + .v4 (all stacked)              (1+2+3+5)

PER-LEVER FINDINGS:
  * Bank-conflict-free pad + .v4 (K1) = THE dominant lever: +3.1-3.4x alone. The
    baseline's unpadded As[64][16]/Bs[16][64] forced 32-bank-stride conflicts on
    the fragment loads AND used scalar (32-bit) global loads — both pathological.
    Padding to +4 floats + float4 vectorized loads removed nearly the whole gap.
  * cp.async double-buffer (K2 over K1) = +0.15x @1024, +0.08x @2048 — a real but
    modest second win (overlaps the global->smem fetch with tensor-core work).
  * Larger 128x64 register tile (K3/K4) DID NOT HELP — it slightly REGRESSED vs the
    64x64 versions. On the consumer card (RTX 5070, few SMs, modest L2) the 64x64 /
    128-thread block already saturates; doubling BM to 128 / 256 threads cuts
    occupancy (more smem + regs per CTA) faster than it raises arithmetic intensity.
    PLATEAU — honest negative for lever 3 on this card.
  * Lever 4 (2 mma.sync in flight) NOT separately needed: ptxas already software-
    pipelines the unrolled inner mma loop once the smem/load bottleneck (K1) is
    removed; the K-loop is no longer mma-latency-bound. Folded as future probe.

BEST CONFIG: K2 — 64x64 block, BK=16, bank-conflict-free smem pad (+4) + float4
(.v4 128-bit) global loads + cp.async double-buffered BK stage. Bit-exact vs the
baseline. 24.49 TFLOP/s @1024 (1.15x off cuBLAS) · 29.75 TFLOP/s @2048 (1.03x off
cuBLAS — essentially parity).

NEW cuBLAS-MULTIPLE: was 3.2-6.9x off (F-BENCH-5). NOW 1.03-1.15x off at D={2048,
1024} with the best bit-exact config. Target (<2.5x) BEATEN by a wide margin;
near full cuBLAS parity reached at 2048 (1.03x) — beyond the honest expectation.

PROMOTION: K2 folded into the production kernel self/native/mma_sm120/
owngemm_sm120.cu (gemm_sm120 / owngemm_sm120 wrapper) so flame's real sm_120
own-GEMM gets the speedup, not just the sweep harness. Bit-exact gate in
owngemm_sm120.cu's GATE mode still PASSes (rel-RMS vs cuBLAS-TF32 ~3e-5).

HONEST (g5): consumer-card cuBLAS-TF32 is also tuned; we did not expect parity but
reached it at 2048 (1.03x). The win was overwhelmingly a layout/load-vectorization
fix (the baseline left bank conflicts + scalar loads on the table); cp.async added
a modest top-up. The register-tile lever PLATEAUED/regressed on this card and was
NOT shipped. All measurements bit-exact (bitdiff=0 vs baseline). NO vast — aiden
free pool only.
