VERDICT: 🔴 1 ROUND-TRIP-LOSSY float→string class FIXED  +  🟢 CONVERGED
         (formatters audited: 3 paths / lossy: 1 default class (4 emit sites) / fixed: 4 sites)

CLAIM
  (A) ROUND-TRIP EXACTNESS — for every double d, parse_float(to_string(d)) == d
      EXACTLY (bit-identical).  FALSIFIER: any d whose emitted string reparses
      to a different double.
  (B) SHORTEST / CLEAN repr — to_string(0.1) == "0.1" (Python repr semantics:
      shortest string that round-trips), not "0.333333" (lossy) nor
      "0.10000000000000001" (over-precise).

ROOT CAUSE (🔴 ROUND-TRIP-LOSSY)
  The DEFAULT float→string format was "%g" (6 significant digits) in EVERY
  non-integer float branch of the C runtime, emitted by the SSOT
  self/runtime_core_emit.hexa (self/runtime_core.c is a gitignored build
  artifact regenerated from it).  4 emit sites shared the lossy default:
    1. hexa_to_cstring  Val-struct float fast path      (was snprintf %g)
    2. hexa_to_cstring  HexaVal float fast path          (was snprintf %g)
    3. _hexa_to_string_rec TAG_FLOAT (no-stdlib build)   (__hexa_print_float_fmt → %g)
    4. hexa_to_string non-integer float (HEXA_HAS_HEXA_RT_STDLIB build) (→ %g)
  plus the shared print path __hexa_format_float_for_print (println/eprintln).
  "%g" with 6 sig digits truncates: 1.0/3.0 → "0.333333" reparses to a
  DIFFERENT double; 2^53+2 → "9.0072e+15", pi → "3.14159", DBL_MAX →
  "1.79769e+308" all LOSE precision.  A user round-tripping a double through
  to_string lost data silently.  (The g15/g17 env opt-ins existed but the
  DEFAULT — what every program gets — was lossy.)

  Also audited: stdlib/runtime/numeric.hexa rt_to_string_scalar float branch
  calls rt_format_float_f(f, 1) (fixed 1-decimal) — but in the live build it
  is reached ONLY for INTEGER-valued floats (the C inline guard handles
  non-integer floats before delegating) → "3.0", correct.  Not a live bug;
  left as-is (the C fix is authoritative for the shipped runtime).

FIX (minimal, in the emitter SSOT — net-additive)
  Replaced the single "%g" default with a 4-mode selector (HEXA_FLOAT_REPR):
    REPR_SHORTEST (NEW DEFAULT) — smallest %.{p}g, p∈[1,17], that reparses
      EXACTLY (strtod is the IEEE-correct inverse; bit-compare via memcpy
      guards -0.0).  Round-trip-SAFE AND shortest = Python repr().
    REPR_G17 / REPR_G15 — fixed-precision escape hatches (g17 round-trips,
      over-precise).
    REPR_G6  — legacy lossy "%g" preserved for golden-snapshot stability.
  All 4 emit sites route through the new __hexa_format_float_mode().  The
  integer-valued "%.1f" convention (trk.27: 3.0 → "3.0") and the NaN/inf
  canonical casing ("NaN"/"inf"/"-inf", PROBE r14-E) are UNCHANGED.
