DESIGN GAP#1 — the 64x64 small-tile (gemm_og17_t64 / MODE_t64), small-D under-fill (D<=512):
================================================================================================
REGIME: at D<=512 the fixed 128x128 tile leaves the 132-SM device catastrophically idle — D=512 ->
  ceil(512/128)^2 = 16 tiles over 132 SMs = 12.1% COVERAGE (>=85% of SMs idle). Stacking more CTAs
  per SM cannot help: there is not even one tile per SM. A 64x64 tile gives 4x the tiles (D=512 -> 64
  tiles = 48.5% coverage), lighting up 4x more SMs. This is a GENUINE under-fill win, DISTINCT from
  the @D=4096 compute-bound cap (which OP-45-GPU/OP-52 measured is NOT tiling-fixable).
TILE / LAUNCH:
  tile 64x64 (1 output tile/CTA) · 1 warpgroup / 128 threads (vs MODE8 2-WG/256-thr, no band split) ·
  ONE wgmma.mma_async m64n64k8.f32.tf32.tf32 per K-step (vs MODE8's 4 = 2 M-bands x 2 N-halves; the
  m64n64k8 CORE *is* a 64x64 output) · ONE 64x64 accumulator float d0[32] (vs MODE8's two d0,d1) ·
  regs ~48 (32 accum + ~16 addressing) -> reg-cap 65536/(48*128)=10 CTA/SM · smem/stage (64+64)*32*4
  =16KB (half of MODE8) -> at NST=2 32KB/CTA -> smem-cap 228/32=7 CTA/SM · OCCUPANCY min(7,10)=7 CTA/SM
  (vs MODE8's 2 — 3.5x the resident pool) · grid plain 1-CTA/tile (NO swizzle, NO persistent — OP-52).
SMEM STAGING: identical ring shape to gemm_og16, halved — NST stages of (Asw[64*32] || Bsw[64*32])
  SWIZZLE_128B-TMA tiles, mbarrier-gated, descriptor-direct (layout_type_=swmode, SBO=1024B), no decode
  band. One tma_load_2d for A(64x32) + ONE for B(64x32)/stage (vs MODE8's NATOM=2 B-loads).
BIT-EXACT K-ACCUMULATION ORDER (the g5 gate — a future build is rel_rms 0 BY CONSTRUCTION):
  the 64x64 tile reuses MODE 8's inner K-loop VERBATIM for its single sub-tile:
     float d0[32]; for(i<32) d0[i]=0;           // ONE 64x64 accumulator
     for(ki=0; ki<nks; ++ki){                    // same K-slab order, TKSW=32
        wait stage; fence;
        for(kk=0; kk<TKSW; kk+=TK) WG(d0,dA,dB); // TK=8 K-sub-step, IDENTICAL to MODE8
        commit_group; wait_group 0; __syncthreads(); }
  This is BYTE-IDENTICAL to the FMA order MODE 8 applies to EACH of its (band, N-half) sub-accumulators
  (WG(d0,dA,dB0) per K-sub-step) — the 64x64 kernel computes ONE such sub-tile/CTA instead of four. NO
  reduction reordered, NO split-K, NO cross-tile accumulation. A future build gates rel_rms 0.000e+00
  vs both the 128x128 reference and CPU-f32 BEFORE any speed number.

================================================================================================
select_config(D,M,N,K) scores EVERY (mode x NST) candidate with the cost model and launches the argmax.
  SELECTABLE = {OG16, OG17, MODE6, MODE8, MODE5_t256, MODE_t64}. The SWIZZLE modes MODE7 (persistent)

OP-52 SWIZZLE ANTI-PREFERENCE — swz_penalty(): applies the OP-52-MEASURED -1.6% factor (0.984) to any
  swizzled mode in the compute-bound/device-filled regime (tiles>=SM_COUNT) — the EXACT regime OP-52

  D>=2048 the GEMM is compute/scheduling-bound (DRAM ~12-40% HBM3 peak), so the swizzle only ADDS index
  overhead -> uniform small regress. The penalty is GATED to the measured regime (neutral at under-fill
  where OP-52 made no measurement — no claim beyond the data).

@D=4096 BIGGER-TILE HYPOTHESIS (gemm_og17_t128x256_2cta) — FUTURE GPU-BUILD item (NOT built here):
================================================================================================
OP-52 closed the CTA-swizzle lever (-1.6%, rasterization/L2 can't help a compute-bound kernel). The
surviving OP-45-GPU T4 lever is a better single-pass per-CTA TILE/schedule. The only in-tree larger
single-pass tile, MODE5 t256 (128x256), is ALREADY closed-neg @4096 (264.9<283.9) because it is
REGISTER-CAPPED to 1 CTA/SM (154 reg/thr). So the candidate is NOT "use t256" — it is a NEW 128x256
tile that gets the wide-tile A-reuse WITHOUT dropping below 2 CTA/SM:
  tile 128x256 (2x B-reuse/A-load -> the +8.5% reuse_eff) · MUST stay 2 CTA/SM (the whole point;
  needs <=128 reg/thr vs t256's 154, e.g. 2-WG-cooperative N-tiling so each WG holds 128x128 of the
  128x256, NOT 4 full N-accumulators; + NST=2=96KB) · deeper single-pass K-pipeline PDEP>=2 to hide
  the 2x-slab drain @nks=128 (the OP-45-GPU T2 stall lives in the per-CTA K-drain, NOT rasterization)
  · NO swizzle (OP-52) · split-K FORBIDDEN (g5).
BIT-EXACT K-ORDER CONSTRAINT (the gate the GPU lane must hold): the 128x256 tile must accumulate each
  output element in the SAME per-K-slab FMA order as MODE 8 — its four 64x64 sub-tiles each run the
  identical `for kk in 0..TKSW step TK: WG(d_sub,dA,dB)` reduction, NO split-K, NO cross-CTA reduction.
  Then rel_rms 0.000e+00 vs the 128x128 reference holds by construction; only THROUGHPUT is open.
COST-MODEL PREDICTION (would it close the gap?) — HONEST: PARTIAL, and ONLY IF 2 CTA/SM holds: if such
  a tile reaches 2 CTA/SM at TN=256, the model credits reuse_eff 1.085 x occ_factor 1.0 (vs t256's 0.86
  @1 CTA/SM) -> ~286.7 x 1.085 ~= 311 TFLOP/s @D=4096 = +8.5% over MODE8 (closing ~1.50x -> ~1.37x), a
  PARTIAL close, NOT full parity (cuBLAS ~427). The model CANNOT predict whether the deeper-K schedule

  so it is a GPU-lane build+measure item, with the explicit RISK that 2-CTA/SM may not be reg-achievable
  at 128x256 (degenerating to the already-closed-neg t256). OP-53 SPECS it; does NOT build it.
