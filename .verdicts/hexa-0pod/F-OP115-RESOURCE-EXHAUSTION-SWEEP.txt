GOAL (g5): GENERALIZE OP-113's regex `{n,m}` ReDoS (an untrusted declared COUNT
drove ~1e9 iterations + multi-GB alloc with no cap) into a CLASS sweep: every
site where an UNTRUSTED parsed count/length/size/repeat drives an ALLOCATION
(array-grow / `.push` / fill) or a LOOP BOUND WITHOUT a sanity cap → a tiny
malicious input forces work/alloc ≫ len(input). This is the unbounded-WORK side,
distinct from OP-105's read-OOB (which bounded the READ to the actual buffer);
here the declared count EXCEEDS any real data and drives the ALLOC/append.

RESULT: 🔴 → FIXED (1) + 🟢 CLEAN census (rest bounded-by-input or documented).
The Verilog frontend's range parser `_rv_parse_range` (in BOTH copies:
stdlib/kernels/logic_synth/read_verilog.hexa AND stdlib/yosys/read_verilog.hexa)
parses a packed/unpacked range `[HI:LO]` into `width = |HI-LO|+1` with NO upper
bound. That width then drives per-bit / per-element WIRE-ALLOCATION loops in the
declaration path (`while bj < width { …rtlil_module_add_wire… }`,
`while k < ur.width { … }` — each a `.push`), so a tiny untrusted Verilog input
`output [999999999:0] o;` forces ~1e9 wire allocations from a few bytes
(CWE-1333 / CWE-400). HI/LO come straight from untrusted source tokens via
`_rv_eval_expr` (the `v = v*10 + d` decimal accumulator). FIXED by capping the
parsed width at `_RV_MAX_WIDTH()` = 1048576 (2^20 — far above any realistic
synthesizable design width) and FAILING the parse fail-closed via the RangeEval
`err` field (every caller already propagates `err` → `ReadVerilogResult.ok=0`)
rather than allocating gigabytes. Pure-additive (+23/−0 each file); zero
valid-parse semantics change (the 12-fixture round-trip gate still 12/12).
