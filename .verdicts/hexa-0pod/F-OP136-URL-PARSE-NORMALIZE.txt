🔴 BUG 1 — PERCENT-DECODE multibyte corruption  (VALUE/encoding · OP-128 class)
────────────────────────────────────────────────────────────────────────────
A %XX escape encodes ONE RAW BYTE, not a Unicode code point. The 3 decoders
emitted `from_char_code(byte)` / `chr(byte)` PER ESCAPE, so under the Rust
interpreter every byte ≥ 0x80 was re-UTF-8-encoded as the code point U+00xx.

EDGE TABLE (input → hexa BEFORE → hexa AFTER fix → Python urllib oracle → V):
  input         hexa-OLD (bytes)        hexa-FIXED       unquote()      verdict
  "%E2%9C%93"   c3 a2 c2 9c c2 93  ✗    e2 9c 93 (✓)     e2 9c 93 (✓)   FIXED
  "%ED%95%9C"   c3 ad c2 95 c2 9c  ✗    ec 95 88 (한)     ec 95 88 (한)   FIXED
  "%41"         41 (A)                  41 (A)           41 (A)         CLEAN
  "hello+world" "hello world"           "hello world"    "hello world"  CLEAN
  "a%2Fb"       "a/b"                   "a/b"            "a/b"          CLEAN(*)
  "%ZZ"         "%ZZ"                   "%ZZ"            "%ZZ"          CLEAN
  "100%"        "100%"                  "100%"           "100%"         CLEAN
  "%4"          "%4"                    "%4"             "%4"           CLEAN
  (*) %2F decodes to the BYTE '/' (correct); this is a leaf decoder with no
      path-splitting downstream, so no premature-reserved-decode security
      issue — the ws parser splits the path BEFORE this decoder ever runs.
  Bounds guard `i+2 < n` AUDITED: correct (index i+2 must be < n = valid);
      trailing complete escape "%41" decodes, partial "%4"/"%"/"a%" verbatim.

FIX: collect decoded raw bytes → bytes_to_str_raw (the OP-135 byte-faithful
SSOT; NUL-clean). Same pattern std_encoding.url_decode already uses. Correct
under BOTH the Rust interpreter and self-host codegen (where chr→hexa_chr_byte
&0xFF happened to be byte-faithful — so this was a runtime-DIVERGENT bug).

────────────────────────────────────────────────────────────────────────────
🔴 BUG 2 — IPv6 AUTHORITY port-confusion  (SECURITY — parse confusion / DoS)
────────────────────────────────────────────────────────────────────────────
_ws_url_parse split host:port on the FIRST ':'. An IPv6 literal "[::1]:8080"
is full of ':' — the first lands INSIDE the address.

EDGE TABLE (ws URL → hexa BEFORE → hexa AFTER fix → urlsplit oracle → verdict):
  url                       hexa-OLD              hexa-FIXED          urlsplit          V
  "ws://[::1]:8080/path"    THREW to_int(        host="::1"          host="::1"        FIXED
                            ":1]:8080") = CRASH   port=8080           port=8080
  "ws://[2001:db8::1]:9000  THREW (crash)         host="2001:db8::1"  host="2001:db8::1" FIXED
   /x"                                            port=9000           port=9000
  "ws://[::1]/path"         host="[" port=80 ✗    host="::1" port=80  host="::1" 80     FIXED
  "ws://host:8080/p"        host="host" 8080      host="host" 8080    host="host" 8080  CLEAN
  "ws://host/p"             host="host" 80        host="host" 80      host="host" 80    CLEAN
  "ws://host"               host="host" 80 /      host="host" 80 /    host="host" 80 /  CLEAN

IMPACT: every IPv6 ws:// URL HARD-CRASHED the parser (`to_int: not an integer`)
— a parse-confusion DoS; under a permissive to_int it would have silently
mis-routed the connection (host="[", wrong port). FIX = bracket-aware split
(RFC 3986 §3.2.2): host = the bracketed span (brackets stripped, matching
urlsplit().hostname), port = the ':' that follows ']' only.
