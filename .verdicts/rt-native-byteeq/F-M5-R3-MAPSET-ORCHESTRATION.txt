1. THE FINDING (c9 — runtime_core_emit.hexa:2967-3031 read, decisive)
================================================================================
hexa_map_set_impl's body is NOT a self-contained raw-mem algorithm (unlike the
read-half rt_map_get_native, which is a pure probe with ZERO extern calls). It is
an ORCHESTRATION of C memory-management primitives:
  · HX_IS_VALSTRUCT(m) → hexa_valstruct_set_by_key  (a whole separate path)
  · hmap_alloc(HMAP_INIT_CAP)                        (lazy table alloc — arena/C)
  · hmap_find(t,key,h)                               (the read-half probe, reusable)
  · t->len*100/t->ht_cap >= HMAP_LOAD_MAX → hmap_grow(t)  (load-factor REHASH — C)
  · hxlcl_strdup(key)                                (key intern — arena/C)
  · order_keys/order_vals append + order_cap*2 grow via malloc/realloc + arena-
    promote (from_arena branch)                      (C heap management)
The pieces that DO the work (alloc, grow/rehash, strdup, realloc) are C functions.
A native rt_map_set_native would CALL those same C functions (extern) — it would
re-wrap the orchestration, NOT replace the substrate. ls drop = the ~50-line
set_impl orchestration only; the heavy lifting (hmap_alloc/grow/strdup) STAYS C.
