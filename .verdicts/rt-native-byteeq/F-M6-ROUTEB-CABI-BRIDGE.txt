================================================================================
1. ROOT CAUSE (decisive, objdump + gdb on aiden x86_64)
================================================================================
measure-5's classification ("val-arena heapify .hexa full port") was WRONG, and
its supporting measurements were taken against a STALE build/hexat (stage_prebuild
_hexat no-ops when build/hexat exists → the supposed native/OFF tests reused a
binary linked against a different arena). Clean-rebuild isolation revealed the
actual root cause:

The native arena seed (self/native/alloc_syscall_x86_64.s, from self/rt/alloc.hexa,
compiled by aprime_cc) uses the HexaVal TWO-REGISTER ABI for every scalar:
  · int ARG  → {rdi = tag, rsi = payload}
  · RETURN   → {rax = tag, rdx = payload}
but runtime_core_emit.hexa declared the seed entries as PLAIN C:
  extern long hexa_arena_head(void);   extern long __blk_used(long b);
  extern void* hexa_arena_alloc(size_t n);   (+ cur/env_lo/env_hi/blk_next/cap/data)
A plain-C caller reads the return from rax (= the TAG, always 0) and passes the
arg in rdi (the seed's TAG slot, leaving the payload it reads from rsi uninit).
Consequences:
  · hexa_arena_on()        → 0  (arena reported OFF → str_concat used malloc, so
                                  the arena path was never even taken)
  · hexa_arena_alloc(n)    → bogus pointer (value was in rdx; rax=tag returned)
  · head/cur/env_lo/hi/blk_*→ 0 / garbage
= the val-arena `cannot subtract non-numeric operand (tag 3 - tag 0)` miscompile
(and, with a partially-correct ABI, a SIGSEGV in hexa_arena_reset/cur).
(hexa_arena_mark/rewind/reset already MATCH the C ABI: HexaArenaMark {block,used}
is the same 16-byte layout the seed returns via __hx_make_val; reset is void(void).)

================================================================================
2. THE FIX (Route B C-ABI bridge — byteeq-inert, opt-in only)
================================================================================
self/runtime_core_emit.hexa, all under #ifdef HEXA_RT_ALLOC_NATIVE:
  · Alias each scalar seed symbol to its TRUE HexaVal signature via
    `extern HexaVal __hxseed_X(...) __asm__("X")` (HexaVal {tag@0,payload@8} ⇒ the
    SysV 16-byte struct ABI passes/returns in exactly the seed's rdi:rsi / rax:rdx
    pairs).
  · Wrap each in a `static inline` __hxw_* that extracts HX_INT (and constructs
    hexa_int(arg) for the arg-taking ones).
  · A function-like #define redirects the plain call-site spelling (hexa_arena_cur()
    etc.) to the __hxw_ wrapper, so the 36 runtime.c call sites stay textually
    unchanged. The seed token inside __asm__("...") is a string literal → never
    macro-expanded → the alias still binds the real seed symbol.
  · forward decls of hexa_arena_alloc guarded under #ifndef HEXA_RT_ALLOC_NATIVE.

fix1 → fix2 history: fix1 named the wrappers with the seed's OWN plain names as
static-inline; clang emitted those as real symbols that SHADOWED the seed → the
__asm__-aliased extern resolved back to the wrapper → INFINITE SELF-RECURSION
(SIGSEGV stack overflow in hexa_arena_cur, RC=139). fix2's distinct __hxw_ names +
#define redirect cured that. fix1 ALREADY removed the `tag 3 - tag 0` error,
confirming the 2-reg ABI diagnosis.

================================================================================
4. NEW WALL (seed-codegen, precisely localized)
================================================================================
__env_extend(base, size) updates the seed's address-envelope globals
__arena_env_lo/hi (g2/g3). The seed disasm shows it WRITES the global PAYLOAD to
[rip+gN] but reads the global TAG from a per-FUNCTION stack slot
(`mov rdi, [rbp-112] # tag g2 from tag-slot`) — and there are ZERO writes to
[rip+gN+8] anywhere in the seed. So a global's TAG half is never persisted to its
.data slot; each call reads the tag from an uninitialised stack slot → garbage tag
→ the int comparisons (`__arena_env_lo == 0`, `base < __arena_env_lo`,
`top > __arena_env_hi`) tag-dispatch through hexa_eq / hexa_cmp_lt / hexa_cmp_gt /
hexa_add_slow on a corrupt tag → fault.

This is a pre-existing aprime_cc MODULE-GLOBAL tagged-value codegen defect
(F-M5-GSLOT-DATA-SLOT area: a global is a 16-byte {payload@g, tag@g+8} HexaVal, but
the global-write path only stores the payload, never the tag, and the global-read
path reads the tag from a stack slot). It was MASKED until now because the broken
C-ABI made hexa_arena_on() return 0, so the arena path (and __env_extend) was never
reached. The C-ABI bridge is what exposed it.
