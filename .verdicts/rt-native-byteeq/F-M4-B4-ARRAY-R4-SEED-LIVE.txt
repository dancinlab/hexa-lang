TL;DR
─────
r4 extended the rt_hi native-seed-into-runtime.a mechanism to the array read-half: a frozen
`self/native/array_core_{x86_64,arm64}.s` seed (native-emitted from array_core.hexa) is
assembled to `build/array_core_native.o`, `HEXA_RT_ARRAY_NATIVE` is defined, and the .o is
ar'd into the shipped runtime.a so `hexa_array_get/set` delegate to the native `rt_array_*_native`
bodies. **PROVEN LIVE+correct on x86_64** (release_build PASS, nm runtime.a = rt_array_*_native T,
real array program exit=6). The honest result: this makes the native bodies LIVE in the shipped
runtime (the M5-relink mechanism proven for the FIRST non-string family) — but it is **NOT a
runtime_core.c byte-DECREASE**: the C `#else` element body STAYS (it is the no-seed fallback for
linux-arm64, which has no native seed). runtime.a +~3.8KB, runtime_core.c +0, `ls self/*.c` +0.

4. WHY NO DECREASE — 🧱 the linux-arm64 no-seed wall (c16, why the #else can't drop)
────────────────────────────────────────────────────────────────────────────────────────
  The rt_str ls-reduction dropped a SEPARATE file (`runtime_hi_gen.c`, ~188 L) from `ls`. The
  array element bodies have NO separate _gen.c — they are inline 1-liner C in runtime_core.c
  (`return HX_ARR_ITEMS(arr)[idx];` / `... = val;`). To get a runtime_core.c byte-DECREASE the
  get/set `#else` must be DROPPED — but that leaves `hexa_array_get/set` with NO body on any
  NO-SEED target. linux-arm64 has NO native seed for ANY family (even rt_str keeps the C path
  there: it links runtime_hi_gen.c, the hexat-transpiled C, on linux-arm64). There is no
  array equivalent of runtime_hi_gen.c, so dropping the #else → undefined `hexa_array_get` on
  linux-arm64 → release_build link FAIL (the F-LEGB-STANDALONE-ELSE-NOGO pattern). So a genuine
  array byte-DECREASE is BLOCKED on **linux-arm64 native codegen maturity** (a campaign-wide
  pre-existing blocker, the same wall flagged in F-LEG-B-CAUSAL-CHAIN) OR a decision to drop
  linux-arm64 array support — NOT resolvable in r4. Honest partial (c9): the LIVE-in-runtime.a
  milestone landed; the byte-DECREASE did not, and the bytes went UP (runtime.a +3.8KB).
